# web-multiAI-tool — 요구사항 정의서

> 최초 작성 2026-08-04 / 상태 1차 확정

---

## 1. 목적

**웹 브라우저에서 텍스트와 이미지로부터 게임 엔진에 바로 넣을 수 있는 3D 에셋을 만드는 것이 이 프로젝트의 목적입니다.** 메시와 텍스처, 리깅, 애니메이션, 효과음을 서로 다른 도구로 나눠 만들지 않고 하나의 타임라인 위에서 함께 만들어냅니다.

목적문에서 가장 중요한 구절은 **"게임 엔진에 바로 넣을 수 있는"** 입니다. 이 구절이 기존 3D 생성 서비스와의 경계선이며, 그래서 완료 조건도 파일을 내보내는 시점이 아니라 Unity에서 실제로 재생되는 시점으로 잡았습니다.

### 1.1 왜 멀티모달인가

**이 도메인에서 멀티모달은 기능 목록의 한 줄이 아니라 성립 조건입니다.**

게임 캐릭터 하나는 단일 산출물이 아니라 기하 형상과 텍스처, 스켈레톤, 모션, 효과음이 결합된 복합체입니다. 단일 모달 AI는 이 중에서 조각 하나만 만들어내기 때문에, 사용자는 여러 서비스를 오가며 결과물을 모으고 손으로 이어 붙여야 합니다. 텍스트에서 메시를, 이미지에서 텍스처를, 텍스트에서 효과음을 만들어내고 여기에 모션을 입히는 각각의 경로가 **하나의 산출물로 수렴해야** 비로소 쓸 수 있는 에셋이 됩니다.

이 수렴이 실제로 일어나는 지점은 D-3의 이벤트 마커와 E-5의 프롬프트 제안입니다. 앞의 것은 애니메이션의 시간 구조를 오디오에 넘기고, 뒤의 것은 애니메이션의 의미를 넘깁니다.

모션만은 성격이 다릅니다. **Tripo의 리타깃은 텍스트에서 모션을 생성하는 것이 아니라 고정 프리셋을 골라 적용하는 방식입니다.** 자세한 내용은 4절의 D-4에 적었습니다.

### 1.2 왜 웹인가

**이 프로젝트는 웹을 기반으로 합니다. 멀티모달 추론은 외부 API나 GPU 서버에서 수행되기 때문에, 브라우저는 결과를 보여주고 편집하는 역할만 담당하면 충분하기 때문입니다.**

무거운 연산이 이미 클라이언트 밖에 있는 구조에서는 두꺼운 데스크톱 애플리케이션을 유지할 이유가 오히려 줄어듭니다. 설치 없이 접근할 수 있다는 점은 부수적으로 따라오는 이점이지 웹을 선택한 주된 근거가 아닙니다.

여기에 기술적인 뒷받침이 하나 더 있습니다. 이 프로젝트가 사용할 후처리 도구 세 가지, 곧 glTF-Transform과 meshoptimizer와 Draco는 모두 JavaScript 또는 WebAssembly로 제공되기 때문에 **브라우저와 서버가 같은 코드를 공유**할 수 있습니다. 브라우저에서 처리하다 실패하거나 데이터가 지나치게 무거운 경우에 서버로 넘겨도 결과가 달라지지 않으며, 폴백 경로를 위해 별도의 구현을 유지할 필요가 없습니다.

### 1.3 차별점 — 생성 이후를 책임진다

**기존 3D 생성 서비스와의 차이는 생성 이후의 공정을 끝까지 가져간다는 점에 있습니다.**

Meshy와 Tripo, Rodin 같은 서비스는 생성 단계에서 작업이 끝납니다. 그 결과로 나온 메시는 토폴로지가 정리되어 있지 않고, UV가 없거나 엉켜 있으며, 스켈레톤과 LOD도 갖추지 못한 상태입니다. 결국 사용자는 파일을 내려받아 Blender로 옮긴 뒤 손을 봐야 하고, 이 지점에서 작업 흐름이 한 번 끊깁니다.

이 프로젝트는 **생성에서 정리를 거쳐 다듬기까지**를 하나의 흐름으로 잇는 것을 차별점으로 삼습니다.

### 1.4 대표 데모 — 이것 하나로 목적이 증명된다

아래 한 장면이 이 프로젝트의 목적을 그대로 증명합니다.

> 텍스트 프롬프트로 캐릭터를 생성한 다음 자동으로 리깅하고, 검을 휘두르는 모션을 붙입니다. 이어서 **타격이 일어나는 프레임에 그 동작에 어울리는 타격음을 생성해 바인딩한 뒤**, Unity로 내보내 그대로 재생합니다.

이 장면이 성립하는 이유는 애니메이션과 효과음이 같은 의미를 공유하기 때문입니다. "검을 휘두른다"는 하나의 의도에서 동작과 소리가 함께 나오므로 한 흐름 안에서 생성하고 정렬할 수 있습니다. 도구를 갈아타며 작업하는 현재 방식에서는 애초에 만들어지기 어려운 장면입니다.

## 2. 목표 / 비목표

**이 프로젝트의 목표는 포트폴리오와 기술 증명이며, 상용 서비스 출시나 본인의 실사용은 목표가 아닙니다.**

이 설정에서 평가 기준이 두 가지로 좁혀집니다.

| 평가 기준 | 무엇을 보는가 |
| --- | --- |
| **완성도** | 1.4절의 대표 데모가 처음부터 끝까지 끊김 없이 동작하는지를 봅니다. 기능이 몇 개인지가 아니라 하나의 흐름이 완결되는지가 기준입니다. |
| **설명 가능성** | 각각의 기술 선택에 근거를 댈 수 있는지를 봅니다. 왜 그 방식을 골랐고 어떤 대안을 왜 버렸는지 설명할 수 있어야 합니다. |

목표를 이렇게 잡았기 때문에 판단이 달라지는 지점이 몇 군데 있습니다. 우선 같은 일을 하는 경쟁 서비스가 이미 존재한다는 사실이 치명적인 문제가 되지 않습니다. 상용 서비스라면 기획을 접을 근거가 되겠지만 여기서는 그렇지 않습니다. 또한 시장 규모나 경쟁사 요금제, 지불 의사를 조사할 필요도 없으며, API 원가 역시 개인이 감당할 수 있는 수준인지만 확인하면 충분합니다.

## 3. 시스템 개요

**전체 구조는 브라우저와 서버, 외부 AI 서비스의 세 층으로 나뉘며, 무거운 연산은 전부 바깥쪽 두 층이 담당합니다.**

브라우저는 씬을 보여주고 편집하는 일을 맡습니다. 3D 뷰포트와 기즈모, 아웃라이너, 인스펙터가 여기에 있고, 애니메이션 타임라인과 오디오 트랙도 브라우저에서 다룹니다. 모든 편집 조작은 커맨드 스택에 쌓여 되돌릴 수 있어야 하며, 후처리 가운데 브라우저에서 감당할 수 있는 작업은 WebAssembly로 그 자리에서 처리합니다.

서버는 외부 API 호출을 중계하고 생성 작업의 상태를 보관하며 산출물 바이너리를 저장합니다. 외부 생성 API는 응답까지 수 분이 걸리는 비동기 작업이므로 서버가 진행 상태를 들고 있다가 클라이언트에 전달합니다. 브라우저에서 후처리가 실패한 경우에는 **같은 모듈을 Node 자식 프로세스로 실행해** 결과를 돌려주는 폴백 경로도 서버가 맡습니다. **씬 편집 상태는 서버에 두지 않고 브라우저에 영속하므로 서버가 내려가도 에디터는 계속 동작합니다.** 인증과 다중 프로젝트는 1차 범위에서 제외했습니다.

외부 AI 서비스는 실제 생성을 수행합니다. 메시와 텍스처, 자동 리깅, 모션 리타깃은 Tripo가 담당하고, 같은 프롬프트로 비교할 대체 경로를 fal.ai의 TRELLIS로 둡니다. 효과음은 ElevenLabs가, 자연어 편집 지시의 해석은 Claude가 처리합니다.

```
 ┌─────────────────── 브라우저 ────────────────────┐
 │  씬 에디터 — three.js / R3F                     │
 │   뷰포트 / 기즈모 / 아웃라이너 / 인스펙터          │
 │   애니메이션 타임라인 + 오디오 트랙               │
 │   커맨드 스택 (undo / redo)                     │
 │   WASM 후처리 — glTF-Transform / meshopt / Draco│
 └───────────────┬─────────────────────────────────┘
                 │  REST + WebSocket (작업 진행률)
 ┌───────────────▼─────────────────────────────────┐
 │  서버 — Spring Boot                             │
 │   외부 API 중계 (키 보관)                        │
 │   생성 작업 큐 / 상태 보관 / 진행률 푸시           │
 │   산출물 바이너리 스토리지                        │
 │   후처리 폴백 — Node 자식 프로세스로              │
 │     shared/postprocess/ 를 그대로 실행            │
 └───────────────┬─────────────────────────────────┘
                 │
 ┌───────────────▼─────────────────────────────────┐
 │  외부 AI                                        │
 │   Tripo — 메시 / 텍스처 / 오토리깅 / 모션 리타깃  │
 │   fal.ai TRELLIS — 메시 대체 경로                │
 │   ElevenLabs Sound Effects — 효과음              │
 │   Claude — 자연어 편집 조수                      │
 └─────────────────────────────────────────────────┘
```

## 4. 기능 요구사항

기능은 일곱 갈래로 나누었고 각 항목에 우선순위를 붙였습니다. **P0는 1.4절의 대표 데모를 성립시키는 데 반드시 필요한 항목이고, P1은 도구로서 쓸 만해지려면 있어야 하는 항목이며, P2는 여력이 남을 때 검토할 항목입니다.** P1과 P2를 전부 잘라내도 대표 데모는 무너지지 않도록 배치했습니다.

### A. 씬 에디터 기반

에디터로서 갖춰야 할 최소한의 기본기입니다. 화면에 드러나지 않지만 없으면 도구 자체가 성립하지 않는 영역입니다.

| ID | 요구사항 | 우선 |
| --- | --- | :---: |
| **A-1** | 3D 뷰포트를 제공합니다. 궤도 회전과 패닝, 줌이 가능한 카메라와 함께 그리드 및 그림자를 표시합니다. | P0 |
| **A-2** | 씬 그래프 아웃라이너를 제공합니다. 계층 구조를 보여주고 선택과 이름 변경, 삭제를 지원합니다. | P0 |
| **A-3** | 이동과 회전, 스케일 기즈모를 제공하며 로컬 좌표계와 월드 좌표계를 전환할 수 있게 합니다. | P0 |
| **A-4** | 인스펙터에서 선택한 노드의 트랜스폼과 머티리얼, 메타데이터를 편집할 수 있게 합니다. | P0 |
| **A-5** | **undo와 redo를 지원합니다.** 모든 편집 조작을 커맨드 객체로 기록해 되돌릴 수 있어야 합니다. | P0 |
| **A-6** | 씬을 직렬화하고 복원합니다. 저장과 불러오기는 물론 새로고침 이후에도 작업 상태가 남아야 합니다. **저장 매체는 H-1의 IndexedDB이며 이 항목은 서버에 의존하지 않습니다.** | P0 |
| **A-7** | 여러 노드를 한 번에 선택하고 일괄로 트랜스폼을 적용할 수 있게 합니다. | P1 |
| **A-8** | 뷰포트에 삼각형 수와 드로콜, 메모리 사용량을 표시합니다. | P1 |

**A-5와 A-6은 데모 화면에 드러나지 않지만 없으면 도구가 성립하지 않는 항목입니다.** 직접 설계하면 개발 기간의 상당 부분을 여기서 소모하게 되므로, three.js 공식 에디터의 Command 패턴을 차용하는 방식으로 대응합니다. 자세한 내용은 8.3절에 적었습니다.

### B. AI 생성 — 생성기 역할

멀티모달 입력을 받아 메시와 텍스처를 만들어내는 부분입니다.

| ID | 요구사항 | 우선 |
| --- | --- | :---: |
| **B-1** | 텍스트 프롬프트로 메시를 생성합니다. Tripo API를 사용합니다. | P0 |
| **B-2** | 이미지를 업로드하거나 끌어다 놓아 메시를 생성합니다. 마찬가지로 Tripo API를 사용합니다. | P0 |
| **B-3** | 텍스처를 생성하고 다시 생성할 수 있게 합니다. 프롬프트를 바꿔 재질을 변경하는 흐름을 지원합니다. | P0 |
| **B-4** | **생성 작업을 비동기로 처리합니다.** 큐에 등록하고 진행률을 표시하며, 실패 시 재시도와 취소를 제공합니다. | P0 |
| **B-5** | 대체 백엔드인 fal.ai TRELLIS로 같은 프롬프트를 생성해 나란히 놓고 비교한 뒤 채택할 수 있게 합니다. | P1 |
| **B-6** | 생성 이력을 남깁니다. 프롬프트와 파라미터, 결과물, 비용을 에셋에 함께 기록합니다. | P1 |

**B-5는 단순한 비교 기능이 아닙니다.** 생성 백엔드를 어댑터 인터페이스 뒤에 두었기 때문에 모델을 갈아 끼울 수 있다는 사실을 화면 위에서 증명하는 항목이며, 동시에 외부 API의 단가 변경이나 서비스 중단에 대한 대비책이기도 합니다.

### C. 후처리 — 후처리기 역할

생성된 메시를 게임에 쓸 수 있는 상태로 다듬는 단계입니다. **파이프라인의 순서는 정리에서 UV, 리깅, LOD로 고정하며 이 순서를 바꾸지 않습니다.**

| ID | 요구사항 | 우선 |
| --- | --- | :---: |
| **C-1** | 지오메트리를 정리합니다. 중복 정점을 병합하고 사용하지 않는 노드와 머티리얼을 제거하며 머티리얼을 병합합니다. glTF-Transform을 사용합니다. **정리 결과는 아래 게이트를 통과해야 다음 단계로 넘어갑니다.** | P0 |
| **C-2** | UV를 언랩합니다. xatlas를 웹워커에서 실행하되, **삼각형이 15만을 넘거나 `SharedArrayBuffer`를 쓸 수 없는 환경이면 시도하지 않고 곧바로 서버(H-5)로 넘깁니다.** 브라우저에서 시작한 뒤에도 웹워커가 45초 안에 결과를 돌려주지 않거나 예외로 끝나면 워커를 종료하고 서버로 전환합니다. 두 임계값은 코드 한 곳의 상수로 두고 흩뿌리지 않습니다. | P0 |
| **C-3** | 자동으로 리깅합니다. Tripo API를 호출하고 생성된 스켈레톤을 화면에 표시합니다. **Tripo가 성공을 반환하더라도 아래 네 가지를 모두 만족해야 성공으로 판정합니다.** | P0 |
| **C-4** | LOD를 생성합니다. 단순화를 반복해 단계를 만들고 `MSFT_lod` 확장으로 기록하며 단계별 폴리곤 수를 보여줍니다. | P1 |
| **C-5** | 메시를 압축합니다. meshoptimizer와 Draco 가운데 선택해 적용하고 전후 용량을 비교해 보여줍니다. | P1 |
| **C-6** | 파이프라인 각 단계의 전후를 미리 보고 되돌릴 수 있게 합니다. | P1 |

순서를 고정하는 이유는 품질이 앞 단계에 종속되기 때문입니다. **AI가 생성한 메시는 토폴로지가 정돈되어 있지 않은 경우가 많고, 이 상태로 리깅에 들어가면 리깅 품질까지 함께 무너집니다.** 따라서 C-3에 진입하기 전에 C-1과 C-2를 반드시 통과시킵니다.

리깅은 외부 API로 처리합니다. 자체적으로 GPU를 두고 오픈소스 모델을 호스팅하는 방식은 상시 인스턴스 비용과 콜드스타트 부담이 있어 범위에서 제외했으며, 이 판단의 근거는 7절에 적었습니다.

**C-1의 완료 게이트는 다섯 가지입니다.** 첫째, 허용 오차 1e-5 안에서 좌표가 같은 중복 정점이 남아 있지 않습니다. 둘째, 참조되지 않는 노드와 머티리얼, 액세서가 0개입니다. 셋째, 면적이 0인 퇴화 삼각형이 0개입니다. 넷째, 정리 전후로 삼각형 수가 줄어들기만 하고 늘지 않으며 메시의 바운딩 박스가 1퍼센트 이내로 보존됩니다. 다섯째, 결과 파일이 `gltf-validator`에서 오류 0으로 통과합니다. 앞의 넷은 glTF-Transform이 이미 뱉는 수치로 판정하고 마지막은 Khronos 공식 패키지를 그대로 씁니다.

**C-3의 성공 판정은 네 가지입니다.** 첫째, 스킨을 가진 메시가 하나 이상 있고 `JOINTS_0`과 `WEIGHTS_0` 어트리뷰트가 존재합니다. 둘째, 본이 2개 이상이며 루트가 하나입니다. 셋째, 가중치 합이 0인 정점이 전체의 1퍼센트 미만입니다. 넷째, D-4의 `slash` 프리셋을 적용해 한 번 재생했을 때 NaN 트랜스폼이 나오지 않고 메시의 월드 바운딩 박스가 원본 대비 10배를 넘지 않습니다. **넷째를 넣은 이유는 리깅이 망가졌을 때 가장 흔한 증상이 정점이 무한히 늘어나는 것이고, 이것이 가장 싸게 잡히는 신호이기 때문입니다.** 하나라도 어긋나면 실패로 표시하고 재시도하거나 다른 프리셋을 제안합니다.

**파이프라인 순서를 고정한 근거는 한 번 측정해 남깁니다.** 같은 생성 메시에 대해 정리와 UV를 거친 뒤 리깅한 결과와, 생성 직후 곧바로 리깅한 결과를 C-3의 판정 기준으로 비교해 표로 남깁니다. **상시 검사가 아니라 1회 실험이며**, 순서를 고정한 이유가 문장이 아니라 수치로 남는 데 목적이 있습니다. 2절의 두 번째 평가 기준에 직접 대응합니다. 결과가 예상과 다르면 순서 고정 자체를 재검토합니다 — 결론을 근거보다 오래 살려두지 않습니다.

C-2의 15만 삼각형과 45초는 실측 전에 잡은 시작값이며, 4단계에서 실측해 이 문서에 반영합니다.

### D. 애니메이션

모션을 적용하고 타임라인 위에서 다루는 부분입니다.

| ID | 요구사항 | 우선 |
| --- | --- | :---: |
| **D-1** | 타임라인을 제공합니다. 재생과 정지, 스크럽이 가능하고 프레임을 표시하며 루프를 지원합니다. | P0 |
| **D-2** | 여러 애니메이션 클립을 보관하고 전환할 수 있게 합니다. | P0 |
| **D-3** | **이벤트 마커를 지원합니다.** 특정 프레임에 이름을 가진 이벤트를 꽂을 수 있어야 합니다. 타격이나 발소리 같은 지점이 여기에 해당합니다. | P0 |
| **D-4** | 모션을 적용합니다. Tripo의 모션 리타깃 API가 제공하는 **고정 프리셋 가운데** 고릅니다. | P0 |
| **D-5** | 키프레임을 직접 편집할 수 있게 합니다. 트랜스폼 트랙을 대상으로 합니다. | P2 |

**D-3은 이 프로젝트의 핵심 구조물입니다.** glTF 명세에는 애니메이션 이벤트라는 개념 자체가 존재하지 않기 때문에 직접 설계해야 하며, 그 설계는 6절에 담았습니다.

**D-4는 임의의 텍스트에서 모션을 만들어내지 못합니다.** Tripo의 리타깃은 `idle` / `walk` / `run` / `jump` / `slash` / `shoot` 같은 **고정 프리셋 열거형**이며, 사족과 다족, 수생 골격에 각각 별도의 목록이 있습니다. 대표 데모의 검을 휘두르는 동작은 `slash` 프리셋으로 성립하므로 데모 자체는 문제가 없지만, 구현자가 임의 모션을 기대하고 들어가지 않도록 여기에 명시합니다.

프리셋 밖의 모션이 필요해지면 대안이 마땅치 않습니다. Mixamo와 모션 생성 오픈소스는 7.1절에서 전부 제외했으므로 **합법적인 출처가 사실상 없습니다.** 1차 범위는 프리셋 안에서 끝내는 것을 전제로 잡았습니다.

### E. 오디오

효과음을 만들고 애니메이션에 붙이는 부분으로, 대표 데모의 마지막 조각에 해당합니다.

| ID | 요구사항 | 우선 |
| --- | --- | :---: |
| **E-1** | 텍스트로 효과음을 생성합니다. ElevenLabs Sound Effects를 사용하며 한 번에 최대 30초까지 만들 수 있습니다. | P0 |
| **E-2** | 오디오 라이브러리를 제공합니다. 생성한 효과음을 보관하고 미리 들을 수 있으며 파형을 표시합니다. | P0 |
| **E-3** | **이벤트 마커에 효과음을 바인딩합니다.** D-3에서 만든 마커에 클립과 볼륨, 피치를 연결합니다. | P0 |
| **E-4** | 타임라인을 재생할 때 효과음이 정확한 타이밍에 울리도록 합니다. | P0 |
| **E-5** | **애니메이션 클립 이름과 이벤트 이름을 근거로 효과음 프롬프트를 자동으로 제안합니다.** 1차 구현은 이름에서 프롬프트를 만드는 규칙 기반 매핑이며, 제안된 문장은 사용자가 그대로 쓰거나 고쳐 쓸 수 있습니다. | P0 |
| **E-6** | 3D 공간 오디오를 지원합니다. 에미터 위치에 따라 감쇠를 적용합니다. | P2 |

E-4에는 구현상의 제약이 하나 붙습니다. **`requestAnimationFrame`이 도는 시점에 맞춰 소리를 트리거하면 타이밍이 어긋납니다.** 렌더 클럭과 오디오 클럭은 서로 다르게 흐르기 때문입니다. 따라서 `AudioContext.currentTime`을 기준으로 삼는 룩어헤드 스케줄러를 두고, 25밀리초 간격으로 돌면서 100밀리초 앞의 소리를 미리 예약하는 방식으로 렌더 클럭과 분리합니다.

**E-5는 대표 데모의 결정타에 해당하는 항목이며, 그래서 P0입니다.** 두 모달을 같은 화면에서 나란히 다루는 데 그치지 않고, 애니메이션이라는 한 모달이 효과음이라는 다른 모달의 입력이 되는 지점이기 때문입니다. "검 휘두르기 애니메이션의 타격 프레임"이라는 맥락에서 타격음 프롬프트가 제안되는 장면이 1.1절의 주장을 가장 직접적으로 보여주며, **이 항목을 잘라내면 1.4절의 데모는 남아도 1.1절의 주장은 증명되지 않습니다.**

1차 구현은 규칙 기반으로 잡습니다. 클립 이름과 이벤트 이름의 조합을 프롬프트 문장에 대응시키는 표 하나면 `slash`와 `hit`에서 "metal sword hitting armor, sharp impact"를 얻을 수 있고, 데모가 요구하는 것은 여기까지입니다. 제안기는 **입력이 이름 쌍이고 출력이 프롬프트 문자열인 하나의 인터페이스** 뒤에 두어, 나중에 F절의 조수를 붙일 때 같은 자리를 LLM 호출로 교체할 수 있게 합니다. 이 교체는 P1로 남기되 데모의 성립을 거기에 걸지 않습니다.

### F. 자연어 조수 — 조수 역할

자연어로 씬을 조작하는 부분입니다.

| ID | 요구사항 | 우선 |
| --- | --- | :---: |
| **F-1** | 채팅 입력으로 씬을 조작합니다. **툴은 두세 개로 한정합니다** — 선택된 객체의 트랜스폼 변경과 머티리얼 변경이면 역할이 증명됩니다. | P0 |
| **F-2** | 씬 상태를 요약한 JSON을 모델에 제공하고, 상세한 내용은 별도의 질의로 가져가게 합니다. | P0 |
| **F-3** | **조수가 실행한 조작도 A-5의 커맨드 스택에 기록해 되돌릴 수 있게 합니다.** | P0 |
| **F-4** | 뷰포트 스크린샷을 맥락으로 함께 전달할 수 있게 합니다. 선택적으로 동작합니다. | P1 |
| **F-5** | 생성과 후처리 파이프라인 자체를 자연어로 지시할 수 있게 합니다. | P1 |

**조수는 새로운 조작 경로를 만들지 않습니다. 이미 있는 에디터 커맨드만 호출합니다.**

이 규칙이 F-3의 비용을 사실상 없앱니다. 조수의 툴 하나가 기존 커맨드 하나에 그대로 대응하면 되돌리기는 자동으로 따라오지만, 조수가 자기만의 씬 변경 경로를 가지면 A절의 커맨드 스택 설계가 오염되고 최대 위험 구간의 난이도가 올라갑니다. 따라서 **커맨드 스택은 1단계에서 외부 호출이 가능한 형태로 설계해두고, 조수 자체는 나중에 붙입니다.**

툴을 두세 개로 묶은 이유는 역할을 증명하는 데 그만큼이면 충분하기 때문입니다. 조수를 둔 근거는 기즈모와 트랜스폼, 머티리얼 조작이라는 3D 편집의 장벽을 낮추는 데 있지 생성에 있지 않습니다. 생성은 이미 B-1이 텍스트 입력으로 받고 있으므로, 조수를 생성 지시로 축소하면 기존 입력창과 구분되지 않으면서 툴 콜링과 씬 요약의 배관 비용만 남습니다.

F-2에는 설계상 지켜야 할 조건이 있습니다. 프롬프트 캐싱은 도구 정의와 시스템 프롬프트, 메시지 순으로 접두사가 일치하는지를 보고 판단하기 때문에, **매 턴 달라지는 씬 상태를 앞쪽에 두면 캐시가 매번 깨집니다.** 따라서 가변적인 씬 상태는 마지막 캐시 분기점 이후, 즉 메시지의 끝에 배치하고 도구 목록의 순서는 고정합니다.

다만 프롬프트 캐싱에는 모델별 최소 접두사 길이가 있고 그 미만이면 마커를 붙여도 조용히 캐시되지 않습니다. 오류가 나지 않고 캐시 적중이 0으로 보고될 뿐입니다. **툴을 두세 개로 묶고 씬 요약도 작게 유지하는 이 설계에서는 애초에 캐시가 걸리지 않을 가능성이 있으므로**, 배치 규칙은 지키되 캐시 효과를 전제로 삼지는 않습니다.

도구 스키마는 `strict: true`와 `additionalProperties: false`를 함께 지정해 모델이 임의의 필드를 만들어내지 못하게 막고, 각 도구의 설명에는 무엇을 하는지뿐 아니라 **언제 호출해야 하는지**를 명시합니다. 이 구조의 선행 사례로는 `ahujasid/blender-mcp`가 있으며, 씬 요약과 개별 조회, 스크린샷의 세 갈래로 상태를 나눠 제공하는 방식을 참고했습니다.

### G. 익스포트

작업 결과를 게임 엔진으로 옮기는 부분이며, 목적문의 "게임 엔진에 바로 넣을 수 있는"을 실제로 검증하는 단계입니다.

| ID | 요구사항 | 우선 |
| --- | --- | :---: |
| **G-1** | glTF와 GLB 형식으로 내보냅니다. | P0 |
| **G-2** | **`extras` 커스텀 스키마로 이벤트 마커와 오디오 바인딩을 직렬화합니다.** 설계는 6.2절에 있습니다. | P0 |
| **G-3** | 오디오 파일을 함께 내보냅니다. GLB에서 외부로 참조하거나 zip으로 묶어 전달합니다. | P0 |
| **G-4** | **Unity 임포터 스크립트를 제공합니다.** `extras`를 읽어 `AnimationEvent`와 `AudioSource`로 복원합니다. | P0 |
| **G-5** | 단위와 축을 변환해 내보내고 관련 옵션을 화면에 노출합니다. | P0 |
| **G-6** | 기존 glTF와 GLB 파일을 불러옵니다. | P1 |

G-5가 필요한 이유는 형식마다 기준이 다르기 때문입니다. **glTF는 미터 단위에 +Y가 위쪽이고 −Z가 정면인 반면, Unity는 같은 +Y 위쪽을 쓰면서도 +Z를 정면으로 삼습니다.** FBX는 여기에 더해 센티미터를 단위로 씁니다. 또한 Unity에는 glTF 기본 임포터가 없어 glTFast나 UnityGLTF가 전제되므로, 이 사실을 사용자에게 문서로 알립니다.

Unreal 경로는 범위에서 제외했습니다. +Z가 위쪽인 데다 좌수 좌표계를 쓰고, Unreal 5의 glTF 스켈레탈 애니메이션 지원도 FBX에 비해 아직 제한적이기 때문입니다. 문의가 있을 경우 FBX 경로를 권장하는 것으로 안내합니다.

| ID | 요구사항 | 우선 |
| --- | --- | :---: |
| **H-1** | 씬 상태를 브라우저의 IndexedDB에 영속합니다. **A-6의 저장 매체는 이것이 정본이며, 서버가 없어도 저장과 새로고침 후 복원이 동작해야 합니다.** | P0 |
| **H-2** | 외부 API가 돌려준 산출물을 서버에 보관합니다. 제공자가 주는 URL은 만료되므로 받은 즉시 내려받아 저장하고 이후에는 서버 URL만 참조합니다. | P0 |
| **H-3** | 생성 작업의 상태를 서버가 보관하고 조회할 수 있게 합니다. **N-4의 이탈 후 복원은 클라이언트가 이 상태를 다시 읽어 성립시킵니다.** | P0 |

| **H-5** | 후처리 폴백 엔드포인트를 제공합니다. **`shared/postprocess/`를 Node 자식 프로세스로 실행하며 C-2가 이 경로를 호출합니다.** | P0 |
| **H-6** | 사용자 인증과 계정 분리를 제공합니다. | P1 |
| **H-7** | 프로젝트를 여러 개 만들고 서버에서 목록으로 관리합니다. | P1 |

**H-6이 P1인 이유는 1.4절의 데모에 로그인 화면이 나오지 않기 때문입니다.** 1차 범위의 서버는 단일 사용자를 전제로 합니다. 다만 이 결정에는 조건이 붙습니다 — **서버를 공개 URL에 노출하지 않습니다.** 로컬 바인딩으로 실행하고 시연은 개발 기기에서 합니다. 살아 있는 링크가 필요하면 인증을 직접 만들지 말고 리버스 프록시의 basic auth나 플랫폼의 접근 제어를 빌립니다. 8.3절에서 Command 패턴을 차용한 것과 같은 판단입니다.

**인증 방식보다 중요한 것이 지출 상한입니다.** N-6의 서버측 하드 캡이 켜져 있으면 접근이 새더라도 최악이 월 $40으로 묶입니다. 무한대와 $40의 차이가 인증의 유무보다 큽니다. 함께 켤 것은 생성 엔드포인트의 시간당 호출 제한, 업로드 크기 상한, 로그에 키를 남기지 않는 것입니다.

**H-5가 서버 런타임을 결정하지는 않습니다.** 폴백이 실행하는 것은 `shared/postprocess/` 하나뿐이고 그 엔드포인트는 100줄 안팎이므로, 이 이점 때문에 서버 언어를 바꾸지 않습니다. 자세한 내용은 8절에 적었습니다.

## 6. 데이터 설계

### 6.1 glTF가 담을 수 없는 것

**glTF에는 오디오도 애니메이션 이벤트도 담을 수 없습니다. 따라서 `extras`에 커스텀 스키마를 두는 것이 유일한 현실적 경로입니다.**

확인한 내용은 이렇습니다. Khronos가 비준한 확장 가운데 오디오를 다루는 것이 없습니다. `KHR_audio_emitter`는 디렉터리 자체가 존재하지 않고, `KHR_audio_graph`는 아직 제안 단계에 머물러 있습니다. `MSFT_audio_emitter`가 있기는 하나 벤더 확장이고 Babylon만 지원하기 때문에 three.js를 쓰는 이 프로젝트에서는 선택지가 되지 못합니다.

애니메이션 쪽은 조금 더 따져볼 여지가 있었습니다. glTF의 기본 애니메이션 채널은 위치와 회전, 스케일, 모프 가중치의 네 가지뿐이지만, **`KHR_animation_pointer`가 비준 확장으로 존재해 JSON 포인터로 머티리얼이나 카메라 같은 임의 속성까지 애니메이션할 수 있습니다.** 그럼에도 결론은 달라지지 않습니다. 이 확장이 넓히는 것은 **무엇을 움직일 수 있는가**이지 **특정 시점에 이름 붙은 사건을 남기는 수단**이 아니며, 이벤트라는 개념은 여전히 명세 어디에도 없습니다.

이 외에도 glTF가 담지 못하는 것들이 있습니다. IK와 본 컨스트레인트, 머티리얼 노드 그래프, 물리와 콜라이더, 스테이트 머신과 블렌드 트리, 커스텀 셰이더가 여기에 해당합니다. 스키닝은 정점 하나가 최대 네 개의 본에만 영향을 받으며 세트를 추가하면 넘길 수 있고, 모프 타깃은 런타임에서 상위 여덟 개까지만 반영됩니다. 이런 제약들은 설계 단계에서 미리 전제해야 나중에 되돌아가는 일이 줄어듭니다.

### 6.2 `extras` 스키마 설계

**애니메이션에는 이벤트를, 씬 루트에는 오디오 클립 목록을 각각 `extras`에 담고, 이벤트가 클립을 이름으로 참조하는 구조로 설계합니다.**

이렇게 나눈 이유는 하나의 효과음을 여러 애니메이션에서 재사용할 수 있어야 하기 때문입니다. 클립 실체를 이벤트마다 중복해 넣는 대신 한곳에 모아두고 참조만 하도록 하면, 같은 타격음을 여러 모션에서 공유할 수 있고 파일 크기도 불필요하게 늘지 않습니다.

**시각은 프레임이 아니라 초로 저장하며, 이것이 유일한 정본입니다.** glTF 애니메이션의 시간축과 Unity의 `AnimationEvent`가 모두 초 단위인데, 그 사이에서 Unity는 임포트할 때 클립을 자체 프레임레이트로 다시 샘플링합니다. 프레임 번호를 정본으로 삼으면 이 재샘플링에서 어긋나므로, 초를 기준으로 두고 프레임은 화면 표시를 위한 참고값으로만 함께 담습니다.

> **필드 이름과 타입, 필수 여부, 검증 단언은 [[WMT_SCHEMA|WMT 스키마 v1]]에 있습니다.** 익스포터와 Unity 임포터가 공유하는 계약이므로 그 문서를 정본으로 삼으며, 여기에 옮겨 적지 않습니다.

설계할 때 지킨 원칙은 네 가지입니다.

첫째, 모든 항목을 `wmt`라는 이름의 네임스페이스 안에 감쌉니다. `extras`는 누구나 자유롭게 쓸 수 있는 자리이므로 다른 도구가 넣은 값과 충돌하지 않게 하기 위해서입니다.

둘째, 스키마에 버전을 함께 담습니다. 나중에 구조를 바꾸더라도 임포터가 버전을 보고 분기할 수 있어야 이미 내보낸 파일이 무용해지지 않습니다.

셋째, **이 스키마를 읽지 못하는 뷰어에서도 모델은 정상적으로 표시되어야 합니다.** `extras`는 명세상 무시해도 무방한 자리이므로, 소리가 나지 않을 뿐 모델이 깨지는 일은 없습니다. 표준을 벗어나면서도 호환성을 잃지 않는 지점이 여기입니다.

넷째, 생성 출처를 함께 남깁니다. 어떤 프롬프트로 만든 소리인지 기록해두면 나중에 같은 결과를 다시 얻거나 조금 바꿔 다시 만들 수 있습니다.

### 6.3 Unity 임포터가 하는 일

**임포터는 glTF가 표현하지 못한 부분을 Unity의 기존 기능으로 복원하는 역할을 합니다.**

glTFast나 UnityGLTF가 모델을 먼저 가져오면, 뒤이어 후처리 스크립트가 `extras`의 `wmt` 영역을 읽습니다. 먼저 오디오 클립 목록을 훑어 각 파일을 Unity의 `AudioClip` 에셋으로 임포트합니다. 그다음 애니메이션마다 기록된 이벤트를 Unity의 `AnimationEvent`로 변환해 해당 클립의 지정된 시각에 꽂습니다. 마지막으로 이 이벤트를 받아 소리를 재생하는 리시버 컴포넌트를 프리팹에 붙이면, 애니메이션을 재생하는 것만으로 정해진 프레임에 효과음이 울립니다.

**이 항목의 결과물은 기능 자체보다 설명 가능성에 있습니다.** 표준에 해당 기능이 없다는 사실을 확인하고, 그 위에서 직접 스키마를 설계한 뒤, 엔진 쪽 임포터까지 붙여 끝을 맺은 과정이 2절의 두 번째 평가 기준과 정확히 맞물립니다.

### 7.1 도입 금지 — 라이선스 판정

**아래 항목들은 라이선스 문제로 도입할 수 없습니다.** 새로운 모델이나 데이터셋을 검토할 때는 코드와 가중치의 라이선스를 각각 따로 확인해야 합니다. 코드가 MIT여도 가중치가 비상업 조건인 사례가 흔하기 때문입니다.

| RigNet | 비상업 라이선스입니다. |
| Mixamo | 공개 API가 존재한다는 근거가 없고, **모션 파일을 재배포하는 것은 약관 위반입니다.** 이 프로젝트는 저장소를 공개하므로 파일을 번들해 올리는 순간 재배포에 해당합니다. 따라서 런타임 연동과 정적 번들 **모두 제외**합니다. |

라이선스를 확인해 사용 가능한 것으로 판정한 항목은 다음과 같습니다. TRELLIS와 TripoSR은 MIT이고, InstantMesh는 Apache-2.0입니다. UniRig는 코드와 가중치가 모두 MIT이며, xatlas와 glTF-Transform, meshoptimizer는 MIT, Draco는 Apache-2.0입니다. three.js와 공식 에디터는 MIT, Babylon.js Editor는 Apache-2.0입니다.

## 8. 기술 스택

```
클라이언트     React 19 + TypeScript + Vite
              @react-three/fiber + drei(기즈모) + leva(인스펙터)
              three.js WebGPURenderer — WebGL2 자동 폴백
              Zustand — 씬 그래프 / 커맨드 스택
              Web Audio API

공유 모듈      shared/postprocess/ — 런타임 중립
              glTF-Transform + meshoptimizer + Draco + xatlas
              브라우저는 웹워커에서, 서버는 Node 자식 프로세스에서 실행

서버          Spring Boot — 외부 API 중계 / 작업 큐 / 스토리지 / STOMP 진행률
              후처리 폴백은 공유 모듈을 Node 자식 프로세스로 실행

외부 API      Tripo — 메시 / 텍스처 / 오토리깅 / 모션 리타깃
              fal.ai TRELLIS — 메시 대체 경로
              ElevenLabs Sound Effects — 효과음
              Claude — 자연어 조수, tool calling
```

**이 구성을 고른 가장 큰 이유는 기존 자산을 그대로 쓸 수 있다는 점입니다.** `C:/dep/3DCommunity`에서 React와 three.js, Spring Boot의 STOMP 조합을 이미 다뤄봤기 때문에 학습에 들어갈 시간을 줄이고 이 프로젝트 고유의 문제에 집중할 수 있습니다.

두 번째 이유는 1.2절에서 언급한 코드 공유입니다. 후처리 도구 세 가지가 전부 JavaScript와 WebAssembly로 제공되므로, 서버 폴백은 브라우저와 같은 모듈을 그대로 실행합니다. 다만 **이 이점의 크기를 부풀리지 않습니다.** 서버가 실행하는 후처리는 C-2의 UV 언랩 하나뿐이고 그 엔드포인트는 100줄 안팎입니다. Spring Boot는 이 모듈을 **Node 자식 프로세스로 호출하며**, 코드 공유를 위해 서버 런타임을 통째로 바꾸지 않습니다. 이점이 엔드포인트 하나에 그친다는 사실을 알면서도 스택 전체를 거기에 맞추는 것은 비례하지 않습니다.

서버를 Node로 통일하는 안도 검토했다가 접었습니다. 런타임을 하나로 줄이는 것처럼 보이지만 실제로는 **익숙하지 않은 영역이 늘어납니다.** 멀티파트 스트리밍과 프로세스 수명 관리, 잡 관리 같은 서버측 Node의 관용구가 새로 붙기 때문입니다. 반면 자식 프로세스 방식이 늘리는 것은 서버 호스트에 Node가 설치되어야 한다는 것 하나이며, 프로세스 기동에 드는 100~300밀리초는 10초에서 45초가 걸리는 작업 앞에서 무의미합니다.

Babylon.js Editor도 후보로 검토했습니다. Apache-2.0 오픈소스라는 점은 매력적이지만 **v5가 Electron 기반 데스크톱 애플리케이션이어서 웹을 타깃으로 하는 이 프로젝트에 재사용할 자산이 없습니다.**

### 8.1 저장소 구조

**단일 저장소로 갑니다.** 기능별로 원격 저장소를 나누면 `shared/postprocess/`가 갈라져 코드 공유라는 이점이 사라지고, 생성부터 Unity까지 관통하는 데모 레일을 한 명령으로 돌릴 수 없게 됩니다. 저장소 분리는 사람이 여럿이고 릴리스 주기가 다를 때 값을 하는데, 여기서는 하나의 논리적 변경이 PR 여러 개로 쪼개지는 비용만 생깁니다.

```
web-multiAI-tool/
  client/          React + R3F 에디터
  server/          Spring Boot
  shared/
    postprocess/   런타임 중립 — 브라우저와 Node 양쪽에서 무수정 실행
    types/         작업 상태 DTO, 단가표
  unity/           C# 임포터
  fixtures/demo/   데모 레일 픽스처
  docs/
```

나중에 떼어낼 후보는 `unity/` 하나뿐입니다. 소비자가 다르고 툴체인도 다르기 때문인데, UPM이 git 저장소의 하위 폴더를 직접 설치할 수 있으므로 **지금 나눌 필요는 없습니다.** 임포터가 에디터와 무관하게 자체 버전을 갖기 시작하면 그때 검토합니다.

### 8.2 되돌릴 수 있게 두는 제약

서버 런타임 결정을 나중에 뒤집더라도 비용이 크지 않도록 아래를 지킵니다.

**`shared/postprocess/`를 런타임 중립으로 유지합니다.** `node:*`도 `window`나 DOM도 import하지 않으며, 입력은 `ArrayBuffer`와 옵션, 출력은 `ArrayBuffer`와 리포트입니다. 그러면 같은 모듈이 웹워커에서도, Node 서버에서도, Spring이 띄운 자식 프로세스에서도 무수정으로 돕니다. **이 제약 하나가 런타임 결정을 거의 공짜로 되돌릴 수 있게 만듭니다.**

**서버를 쓰기 전에 HTTP 계약을 먼저 확정합니다.** 클라이언트는 프레임워크가 아니라 계약에 대고 코딩합니다.

**클라이언트의 서버 호출은 한 파일만 거칩니다.** 컴포넌트에 `fetch`를 흩뿌리지 않습니다.

**작업의 영속 정체성은 제공자가 준 작업 ID입니다.** 진실의 원천은 외부 API이고 우리 레코드는 포인터이므로, 서버를 다시 써도 진행 중인 작업이 살아남습니다.

**서버가 도메인 모델을 정의하지 못하게 합니다.** 씬의 정본은 H-1의 IndexedDB이고 서버는 해석하지 않는 블롭과 메타만 보관합니다. 도메인을 모르는 서버는 교체가 쉽습니다.

되돌릴 수 없게 되는 지점은 **3단계의 어댑터 계층**입니다. 외부 API 호출과 오류 분류, 비용 회계, 작업 폴링이 서버측 최대 작업량이고 언어에 묶입니다. 그 전까지는 문서 수정으로 끝납니다.

### 8.3 차용 — three.js 공식 에디터

**A절의 기본기 항목들은 직접 설계하지 않고 three.js 공식 에디터의 Command 패턴을 차용합니다.**

undo와 redo, 씬 직렬화, 다중 선택, 카메라 조작은 화면에 드러나지 않으면서 개발 기간을 크게 소모하는 영역입니다. 공식 에디터가 MIT 라이선스라 가져다 쓰는 데 법적 문제가 없고, 이미 검증된 구조이므로 설계에 시간을 들이지 않아도 됩니다. 이 구간을 줄일 수 있는 사실상 유일한 방법입니다.
