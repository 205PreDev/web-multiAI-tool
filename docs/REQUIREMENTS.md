# web-multiAI-tool — 요구사항 정의서 v2

> 최초 작성 2026-08-04 / 1차 확정 2026-08-08 / **2차 확정 2026-08-10 — 목표를 공개 서비스급으로 확장**
> 시스템 구조와 데이터 모델, API 계약은 [[ARCHITECTURE]]에, 화면과 흐름은 [[UX]]에 있습니다. 이 문서는 무엇을 만들고 어떤 기준으로 끝났다고 판정하는지만 담습니다.

## 1. 목적

**웹 브라우저에서 텍스트와 이미지로부터 게임 엔진에 바로 넣을 수 있는 3D 에셋을 만드는 것이 이 프로젝트의 목적입니다.** 메시와 텍스처, 리깅, 애니메이션, 효과음을 서로 다른 도구로 나눠 만들지 않고 하나의 타임라인 위에서 함께 만들어냅니다.

v2에서 목적문에 한 문장이 더해집니다. **이 도구를 낯선 사용자가 URL 하나로 접속해 계정을 만들고, 에셋을 만들어 공유 링크로 내보낼 수 있는 공개 웹 서비스로 완성합니다.** 파이프라인이 한 사람의 데모로 끝나지 않고, 계정과 쿼터, 공유, 협업을 갖춘 하나의 잘 만든 웹 제품으로 서는 것까지가 v2의 범위입니다.

목적문에서 가장 중요한 구절은 여전히 **"게임 엔진에 바로 넣을 수 있는"** 입니다. 이 구절이 기존 3D 생성 서비스와의 경계선이며, 그래서 완료 조건도 파일을 내보내는 시점이 아니라 Unity에서 실제로 재생되는 시점으로 잡았습니다.

### 1.1 왜 멀티모달인가

**이 도메인에서 멀티모달은 기능 목록의 한 줄이 아니라 성립 조건입니다.**

게임 캐릭터 하나는 단일 산출물이 아니라 기하 형상과 텍스처, 스켈레톤, 모션, 효과음이 결합된 복합체입니다. 단일 모달 AI는 이 중에서 조각 하나만 만들어내기 때문에, 사용자는 여러 서비스를 오가며 결과물을 모으고 손으로 이어 붙여야 합니다. 텍스트에서 메시를, 이미지에서 텍스처를, 텍스트에서 효과음을 만들어내고 여기에 모션을 입히는 각각의 경로가 **하나의 산출물로 수렴해야** 비로소 쓸 수 있는 에셋이 됩니다.

이 수렴이 실제로 일어나는 지점은 D-3의 이벤트 마커와 E-5의 프롬프트 제안입니다. 앞의 것은 애니메이션의 시간 구조를 오디오에 넘기고, 뒤의 것은 애니메이션의 의미를 넘깁니다.

모션만은 성격이 다릅니다. **Tripo의 리타깃은 텍스트에서 모션을 생성하는 것이 아니라 고정 프리셋을 골라 적용하는 방식입니다.** 자세한 내용은 4절의 D-4에 적었습니다.

### 1.2 왜 웹인가

**멀티모달 추론은 외부 API나 GPU 서버에서 수행되므로 브라우저는 결과를 보여주고 편집하는 역할만 담당하면 충분합니다.** 무거운 연산이 이미 클라이언트 밖에 있는 구조에서는 두꺼운 데스크톱 애플리케이션을 유지할 이유가 오히려 줄어듭니다.

v2에서 이 논거는 하나 더 강해집니다. **공유 링크가 곧 실행 환경입니다.** 만든 에셋을 다른 사람에게 보여주는 데 설치도 다운로드도 필요 없이 URL 하나면 되고, 받은 사람의 브라우저가 그대로 3D 뷰어가 됩니다. 에셋 허브(J절)와 협업(K절)은 웹이 아니면 이 형태로 존재할 수 없습니다.

기술적인 뒷받침도 유지됩니다. 후처리 도구 세 가지 — glTF-Transform과 meshoptimizer, Draco — 는 모두 JavaScript 또는 WebAssembly로 제공되기 때문에 **브라우저와 서버가 같은 코드를 공유**할 수 있습니다. 브라우저에서 처리하다 실패하면 서버로 넘겨도 결과가 달라지지 않습니다.

### 1.3 차별점 — 생성 이후를 책임진다

**기존 3D 생성 서비스와의 차이는 생성 이후의 공정을 끝까지 가져간다는 점에 있습니다.**

Meshy와 Tripo, Rodin 같은 서비스는 생성 단계에서 작업이 끝납니다. 그 결과로 나온 메시는 토폴로지가 정리되어 있지 않고, UV가 없거나 엉켜 있으며, 스켈레톤과 LOD도 갖추지 못한 상태입니다. 결국 사용자는 파일을 내려받아 Blender로 옮긴 뒤 손을 봐야 하고, 이 지점에서 작업 흐름이 한 번 끊깁니다.

이 프로젝트는 **생성에서 정리를 거쳐 다듬기, 그리고 공유까지**를 하나의 흐름으로 잇습니다. v2의 에셋 허브는 이 차별점의 자연스러운 연장입니다 — 다듬어진 에셋은 파일로 흩어지는 대신 버전 이력과 생성 계보를 가진 채 허브에 남고, 링크로 공유되며, 갤러리에서 발견됩니다.

### 1.4 대표 데모 A — 파이프라인 증명

아래 한 장면이 이 프로젝트의 기술적 목적을 그대로 증명합니다.

> 텍스트 프롬프트로 캐릭터를 생성한 다음 자동으로 리깅하고, 검을 휘두르는 모션을 붙입니다. 이어서 **타격이 일어나는 프레임에 그 동작에 어울리는 타격음을 생성해 바인딩한 뒤**, Unity로 내보내 그대로 재생합니다.

이 장면이 성립하는 이유는 애니메이션과 효과음이 같은 의미를 공유하기 때문입니다. "검을 휘두른다"는 하나의 의도에서 동작과 소리가 함께 나오므로 한 흐름 안에서 생성하고 정렬할 수 있습니다. 도구를 갈아타며 작업하는 현재 방식에서는 애초에 만들어지기 어려운 장면입니다.

### 1.5 대표 데모 B — 서비스 증명

v2가 더한 두 번째 장면입니다.

> 처음 방문한 사용자가 공개 갤러리에서 다른 사람이 만든 에셋을 브라우저로 돌려보다가, 소셜 계정으로 가입합니다. 가입과 함께 받은 무료 크레딧으로 자신의 캐릭터를 하나 만들어 리깅과 효과음까지 붙이고, **공유 링크를 발행해 다른 기기의 브라우저에서 그 에셋이 재생되는 것을 확인합니다.** 크레딧이 얼마 쓰였고 얼마 남았는지가 화면에서 그대로 읽힙니다.

데모 A가 "이 파이프라인이 기술적으로 성립한다"를 증명한다면, 데모 B는 **"이것이 낯선 사람에게 내놓을 수 있는 제품이다"**를 증명합니다. 계정과 쿼터, 공유, 실패 처리, 비용 표시가 전부 이 장면 하나에 걸립니다.

## 2. 목표 / 비목표

**v1의 목표였던 포트폴리오와 기술 증명은 유지되고, 공개 서비스로서의 완성이 더해집니다.** 상용 수익화 — 결제, 구독, 마케팅 — 는 여전히 목표가 아닙니다.

평가 기준은 셋입니다.

| 평가 기준 | 무엇을 보는가 |
| --- | --- |
| **완성도** | 1.4절 데모 A와 1.5절 데모 B가 처음부터 끝까지 끊김 없이 동작하는지를 봅니다. 기능이 몇 개인지가 아니라 흐름이 완결되는지가 기준입니다. |
| **설명 가능성** | 각각의 기술 선택에 근거를 댈 수 있는지를 봅니다. 왜 그 방식을 골랐고 어떤 대안을 왜 버렸는지 설명할 수 있어야 합니다. |
| **서비스 품질** | 낯선 사용자 기준의 품질입니다. 온보딩 없이도 첫 생성에 도달하는가, 실패가 이해 가능한 언어로 표시되는가, 남용이 방어되는가, 비용이 통제되는가를 봅니다. |

목표가 이렇게 잡혔으므로 v1에서 "치명적이지 않다"고 정리했던 판단 일부가 되돌아옵니다. 경쟁 서비스의 존재는 여전히 기획을 접을 근거가 아니지만, **공개 서비스인 이상 남용 방어와 비용 통제는 선택이 아니라 성립 조건이 됩니다.** 생성 API는 호출마다 실비가 나가므로, 인증도 쿼터도 없는 공개 생성 서비스는 하루면 예산이 증발합니다.

**비목표를 명시합니다.** 결제와 구독 과금은 범위 밖이며 설계 여지만 [[ROADMAP]]에 남깁니다. 수평 확장(다중 인스턴스)은 목표가 아니고 단일 인스턴스에서 정확히 동작하는 것이 목표입니다 — 확장 경로는 [[ARCHITECTURE]]에 적어두되 구현하지 않습니다.

## 3. 시스템 개요

**전체 구조는 브라우저와 서버, 외부 AI 서비스의 세 층으로 나뉘며, 무거운 연산은 전부 바깥쪽 두 층이 담당합니다.**

브라우저는 씬을 보여주고 편집합니다. 3D 뷰포트와 기즈모, 아웃라이너, 인스펙터, 애니메이션 타임라인과 오디오 트랙이 여기에 있습니다. 모든 편집 조작은 커맨드 스택에 쌓여 되돌릴 수 있고, 후처리 가운데 브라우저에서 감당할 수 있는 작업은 WebAssembly로 그 자리에서 처리합니다. **편집은 로컬 우선입니다** — IndexedDB에 항상 영속하므로 네트워크가 끊기거나 서버가 내려가도 편집은 계속되고, 연결이 돌아오면 서버와 동기화합니다.

서버의 역할이 v2에서 늘어납니다. v1의 세 가지 — 키 중계, 작업 상태 보관, 후처리 폴백 — 에 더해 **계정과 크레딧 원장, 프로젝트·에셋의 정본 저장, 공유 링크, 협업 세션 중계**를 맡습니다. 다만 서버가 씬의 내용을 해석하지는 않습니다. 씬은 버전이 붙은 불투명한 리비전으로 저장되고, lock의 대상인 노드 ID도 서버에게는 문자열일 뿐입니다. **도메인을 모르는 서버는 교체가 쉽다**는 v1의 원칙은 유지됩니다.

외부 AI 서비스는 실제 생성을 수행합니다. 메시와 텍스처, 자동 리깅, 모션 리타깃은 Tripo가 담당하고, 같은 프롬프트로 비교할 대체 경로를 fal.ai의 TRELLIS로 둡니다. 효과음은 ElevenLabs가, 자연어 편집 지시의 해석과 VLM 검수는 Claude가 처리합니다.

```
 ┌─────────────────── 브라우저 ────────────────────┐
 │  씬 에디터 — three.js / R3F                     │
 │   뷰포트 / 기즈모 / 아웃라이너 / 인스펙터          │
 │   애니메이션 타임라인 + 오디오 트랙               │
 │   커맨드 스택 (undo / redo)                     │
 │   WASM 후처리 — glTF-Transform / meshopt / Draco│
 │   IndexedDB — 로컬 우선 영속 + 동기화 큐          │
 │  공개 화면 — 갤러리 / 공유 뷰어 (로그인 불필요)    │
 └───────────────┬─────────────────────────────────┘
                 │  REST + WebSocket (진행률 / 협업)
 ┌───────────────▼─────────────────────────────────┐
 │  서버 — Spring Boot                             │
 │   인증(OAuth) / 크레딧 원장 / 남용 방어           │
 │   외부 API 중계 (키 보관)                        │
 │   생성 작업 큐 / 상태 보관 / 진행률 푸시           │
 │   프로젝트·에셋 정본 저장 (리비전, 해석하지 않음)   │
 │   공유 링크 / 갤러리 / 협업 lock 중계             │
 │   후처리 폴백 — Node 자식 프로세스로              │
 │     shared/postprocess/ 를 그대로 실행            │
 │   PostgreSQL + S3 호환 오브젝트 스토리지          │
 └───────────────┬─────────────────────────────────┘
                 │
 ┌───────────────▼─────────────────────────────────┐
 │  외부 AI                                        │
 │   Tripo — 메시 / 텍스처 / 오토리깅 / 모션 리타깃  │
```

컴포넌트 경계와 데이터 모델, API 계약, 배포 토폴로지는 [[ARCHITECTURE]]가 정본입니다.

## 4. 기능 요구사항

기능은 열두 갈래로 나누었고 각 항목에 우선순위를 붙였습니다. **v2에서 우선순위의 의미가 재정의됩니다.**

| 우선 | 의미 | 완료 조건과의 관계 |
| :---: | --- | --- |
| **P0** | 1.4절 **데모 A**를 성립시키는 데 반드시 필요 | 이것만으로 데모 A가 돕니다 |
| **P1** | 1.5절 **데모 B** — 공개 서비스로 성립하는 데 필요. 도구로서의 기본 품질 포함 | P0+P1로 데모 B가 돕니다 |
| **P2** | 차별화 확장 — 협업, 검수자, 에디터 심화 | 잘라도 두 데모가 무너지지 않습니다 |

구현 순서는 여전히 위험 우선입니다. P0를 먼저 완성해 데모 A를 세우고, P1로 서비스를 세우고, P2를 얹습니다. **P1 항목이라도 서버 스키마나 계약에 영향을 주는 것은 P0 단계에서 자리만 미리 파둡니다** — 예를 들어 모든 서버 레코드는 처음부터 `user_id`를 갖습니다. 자세한 순서는 `TODO.md`에 있습니다.

### A. 씬 에디터 기반

에디터로서 갖춰야 할 최소한의 기본기입니다. 화면에 드러나지 않지만 없으면 도구 자체가 성립하지 않는 영역입니다.

| ID | 요구사항 | 우선 |
| --- | --- | :---: |
| **A-1** | 3D 뷰포트를 제공합니다. 궤도 회전과 패닝, 줌이 가능한 카메라와 함께 그리드 및 그림자를 표시합니다. | P0 |

### C. 후처리 — 후처리기 역할

생성된 메시를 게임에 쓸 수 있는 상태로 다듬는 단계입니다. **파이프라인의 순서는 정리에서 UV, 리깅, LOD로 고정하며 이 순서를 바꾸지 않습니다.**

| ID | 요구사항 | 우선 |
| --- | --- | :---: |
| **C-1** | 지오메트리를 정리합니다. 중복 정점을 병합하고 사용하지 않는 노드와 머티리얼을 제거하며 머티리얼을 병합합니다. glTF-Transform을 사용합니다. **정리 결과는 아래 게이트를 통과해야 다음 단계로 넘어갑니다.** | P0 |

순서를 고정하는 이유는 품질이 앞 단계에 종속되기 때문입니다. **AI가 생성한 메시는 토폴로지가 정돈되어 있지 않은 경우가 많고, 이 상태로 리깅에 들어가면 리깅 품질까지 함께 무너집니다.** 따라서 C-3에 진입하기 전에 C-1과 C-2를 반드시 통과시킵니다.

리깅은 외부 API로 처리합니다. 자체적으로 GPU를 두고 오픈소스 모델을 호스팅하는 방식은 상시 인스턴스 비용과 콜드스타트 부담이 있어 범위에서 제외했으며, 이 판단의 근거는 7절에 적었습니다.

**C-1의 완료 게이트는 다섯 가지입니다.** 첫째, 허용 오차 1e-5 안에서 좌표가 같은 중복 정점이 남아 있지 않습니다. 둘째, 참조되지 않는 노드와 머티리얼, 액세서가 0개입니다. 셋째, 면적이 0인 퇴화 삼각형이 0개입니다. 넷째, 정리 전후로 삼각형 수가 줄어들기만 하고 늘지 않으며 메시의 바운딩 박스가 1퍼센트 이내로 보존됩니다. 다섯째, 결과 파일이 `gltf-validator`에서 오류 0으로 통과합니다. 앞의 넷은 glTF-Transform이 이미 뱉는 수치로 판정하고 마지막은 Khronos 공식 패키지를 그대로 씁니다.

**C-3의 성공 판정은 네 가지입니다.** 첫째, 스킨을 가진 메시가 하나 이상 있고 `JOINTS_0`과 `WEIGHTS_0` 어트리뷰트가 존재합니다. 둘째, 본이 2개 이상이며 루트가 하나입니다. 셋째, 가중치 합이 0인 정점이 전체의 1퍼센트 미만입니다. 넷째, D-4의 `slash` 프리셋을 적용해 한 번 재생했을 때 NaN 트랜스폼이 나오지 않고 메시의 월드 바운딩 박스가 원본 대비 10배를 넘지 않습니다. **넷째를 넣은 이유는 리깅이 망가졌을 때 가장 흔한 증상이 정점이 무한히 늘어나는 것이고, 이것이 가장 싸게 잡히는 신호이기 때문입니다.** 하나라도 어긋나면 실패로 표시하고 재시도하거나 다른 프리셋을 제안합니다.

**파이프라인 순서를 고정한 근거는 한 번 측정해 남깁니다.** 같은 생성 메시에 대해 정리와 UV를 거친 뒤 리깅한 결과와, 생성 직후 곧바로 리깅한 결과를 C-3의 판정 기준으로 비교해 표로 남깁니다. **상시 검사가 아니라 1회 실험이며**, 순서를 고정한 이유가 문장이 아니라 수치로 남는 데 목적이 있습니다. 결과가 예상과 다르면 순서 고정 자체를 재검토합니다 — 결론을 근거보다 오래 살려두지 않습니다.

C-2의 15만 삼각형과 45초는 실측 전에 잡은 시작값이며, 4단계에서 실측해 이 문서에 반영합니다.

E-4에는 구현상의 제약이 하나 붙습니다. **`requestAnimationFrame`이 도는 시점에 맞춰 소리를 트리거하면 타이밍이 어긋납니다.** 렌더 클럭과 오디오 클럭은 서로 다르게 흐르기 때문입니다. 따라서 `AudioContext.currentTime`을 기준으로 삼는 룩어헤드 스케줄러를 두고, 25밀리초 간격으로 돌면서 100밀리초 앞의 소리를 미리 예약하는 방식으로 렌더 클럭과 분리합니다.

1차 구현은 규칙 기반으로 잡습니다. 클립 이름과 이벤트 이름의 조합을 프롬프트 문장에 대응시키는 표 하나면 `slash`와 `hit`에서 "metal sword hitting armor, sharp impact"를 얻을 수 있고, 데모가 요구하는 것은 여기까지입니다. 제안기는 **입력이 이름 쌍이고 출력이 프롬프트 문자열인 하나의 인터페이스** 뒤에 두어, 나중에 F절의 조수를 붙일 때 같은 자리를 LLM 호출로 교체할 수 있게 합니다. 이 교체는 P1로 남기되 데모의 성립을 거기에 걸지 않습니다.

| **F-2** | 씬 상태를 요약한 JSON을 모델에 제공하고, 상세한 내용은 별도의 질의로 가져가게 합니다. | P0 |
| **F-3** | **조수가 실행한 조작도 A-5의 커맨드 스택에 기록해 되돌릴 수 있게 합니다.** | P0 |
| **F-4** | 뷰포트 스크린샷을 맥락으로 함께 전달할 수 있게 합니다. 선택적으로 동작합니다. | P1 |
| **F-5** | 생성과 후처리 파이프라인 자체를 자연어로 지시할 수 있게 합니다. | P1 |

**조수는 새로운 조작 경로를 만들지 않습니다. 이미 있는 에디터 커맨드만 호출합니다.**

이 규칙이 F-3의 비용을 사실상 없앱니다. 조수의 툴 하나가 기존 커맨드 하나에 그대로 대응하면 되돌리기는 자동으로 따라오지만, 조수가 자기만의 씬 변경 경로를 가지면 A절의 커맨드 스택 설계가 오염되고 최대 위험 구간의 난이도가 올라갑니다. 따라서 **커맨드 스택은 1단계에서 외부 호출이 가능한 형태로 설계해두고, 조수 자체는 나중에 붙입니다.**

툴을 두세 개로 묶은 이유는 역할을 증명하는 데 그만큼이면 충분하기 때문입니다. 조수를 둔 근거는 기즈모와 트랜스폼, 머티리얼 조작이라는 3D 편집의 장벽을 낮추는 데 있지 생성에 있지 않습니다. 생성은 이미 B-1이 텍스트 입력으로 받고 있으므로, 조수를 생성 지시로 축소하면 기존 입력창과 구분되지 않으면서 툴 콜링과 씬 요약의 배관 비용만 남습니다.

F-2에는 설계상 지켜야 할 조건이 있습니다. 프롬프트 캐싱은 도구 정의와 시스템 프롬프트, 메시지 순으로 접두사가 일치하는지를 보고 판단하기 때문에, **매 턴 달라지는 씬 상태를 앞쪽에 두면 캐시가 매번 깨집니다.** 따라서 가변적인 씬 상태는 마지막 캐시 분기점 이후, 즉 메시지의 끝에 배치하고 도구 목록의 순서는 고정합니다.

다만 프롬프트 캐싱에는 모델별 최소 접두사 길이가 있고 그 미만이면 마커를 붙여도 조용히 캐시되지 않습니다. 오류가 나지 않고 캐시 적중이 0으로 보고될 뿐입니다. **툴을 두세 개로 묶고 씬 요약도 작게 유지하는 이 설계에서는 애초에 캐시가 걸리지 않을 가능성이 있으므로**, 배치 규칙은 지키되 캐시 효과를 전제로 삼지는 않습니다.

도구 스키마는 `strict: true`와 `additionalProperties: false`를 함께 지정해 모델이 임의의 필드를 만들어내지 못하게 막고, 각 도구의 설명에는 무엇을 하는지뿐 아니라 **언제 호출해야 하는지**를 명시합니다. 이 구조의 선행 사례로는 `ahujasid/blender-mcp`가 있으며, 씬 요약과 개별 조회, 스크린샷의 세 갈래로 상태를 나눠 제공하는 방식을 참고했습니다.

작업 결과를 게임 엔진으로 옮기는 부분이며, 목적문의 "게임 엔진에 바로 넣을 수 있는"을 실제로 검증하는 단계입니다.

| **G-2** | **`extras` 커스텀 스키마로 이벤트 마커와 오디오 바인딩을 직렬화합니다.** 설계는 6.2절에 있습니다. | P0 |
| **G-3** | 오디오 파일을 함께 내보냅니다. GLB에서 외부로 참조하거나 zip으로 묶어 전달합니다. | P0 |

G-5가 필요한 이유는 형식마다 기준이 다르기 때문입니다. **glTF는 미터 단위에 +Y가 위쪽이고 −Z가 정면인 반면, Unity는 같은 +Y 위쪽을 쓰면서도 +Z를 정면으로 삼습니다.** FBX는 여기에 더해 센티미터를 단위로 씁니다. 또한 Unity에는 glTF 기본 임포터가 없어 glTFast나 UnityGLTF가 전제되므로, 이 사실을 사용자에게 문서로 알립니다.

Unreal 경로는 범위에서 제외했습니다. +Z가 위쪽인 데다 좌수 좌표계를 쓰고, Unreal 5의 glTF 스켈레탈 애니메이션 지원도 FBX에 비해 아직 제한적이기 때문입니다. 문의가 있을 경우 FBX 경로를 권장하는 것으로 안내합니다.

### I. 계정과 크레딧

공개 서비스의 성립 조건입니다. **생성 API는 호출마다 실비가 나가므로, 계정과 쿼터 없이 생성 엔드포인트를 공개하는 것은 예산을 공개하는 것과 같습니다.**

| ID | 요구사항 | 우선 |
| --- | --- | :---: |
| **I-1** | **소셜 OAuth로 로그인합니다.** Google과 GitHub를 지원하며 자체 이메일·비밀번호 가입은 두지 않습니다. 갤러리와 공유 뷰어는 로그인 없이 접근됩니다. | P1 |
| **I-2** | **사용자별 크레딧 원장을 둡니다.** 가입 시 무료 크레딧을 지급하고, 생성 호출마다 예상 비용을 선차감 후 실비로 정산합니다. 모든 증감이 원장 행으로 남아 잔액이 언제나 재계산 가능해야 합니다. | P1 |
| **I-3** | **호출 전에 예상 크레딧을 보여주고, 잔액이 부족하면 호출 자체를 막습니다.** 헤더에 잔액을 상시 표시합니다. | P1 |

| **I-7** | 프로젝트를 여러 개 만들고 대시보드에서 목록으로 관리합니다. 이름과 썸네일, 마지막 수정 시각을 보여줍니다. | P1 |

**결제는 두지 않습니다.** 크레딧은 무료 지급분과 BYOK로만 충전되며, 유료 충전 설계는 [[ROADMAP]]에 여지만 남깁니다. 무료 지급량은 9절의 크레딧 환산에 따라 **가입 시 200크레딧(전체 파이프라인 캐릭터 2~3개 분량)**으로 시작하고 운영하며 조정합니다.

I-1에서 자체 비밀번호를 두지 않는 이유는 셋입니다. 비밀번호 저장과 재설정 흐름이라는 보안 표면 전체가 사라지고, 일회용 이메일 가입 봇을 OAuth 제공자의 계정 검증에 떠넘길 수 있으며, 데모 B의 온보딩이 클릭 두 번으로 줄어듭니다.

### J. 에셋 허브와 공유

만든 것이 파일로 흩어지지 않고 서비스 안에 남아 발견되는 영역입니다. **공유 링크가 곧 실행 환경이라는 1.2절의 논거를 실제 기능으로 만드는 곳입니다.**

| ID | 요구사항 | 우선 |
| --- | --- | :---: |
| **J-1** | **공개 갤러리를 제공합니다.** 사용자가 공개로 전환한 에셋이 썸네일 격자로 노출되고, 로그인 없이 열람할 수 있습니다. 최신순 정렬이면 충분하며 검색·태그는 P2입니다. | P1 |
| **J-2** | **에셋 공유 링크를 발행합니다.** 링크는 특정 버전을 가리키는 취소 가능한 토큰이며, 소유자가 회수하면 즉시 무효화됩니다. | P1 |
| **J-3** | **공유 뷰어를 제공합니다.** 링크를 연 브라우저에서 로그인 없이 3D 모델이 궤도 카메라로 표시되고, 애니메이션 클립을 골라 재생하면 **바인딩된 효과음이 이벤트 시점에 함께 울립니다.** 에디터가 아니라 읽기 전용 뷰어이며 모바일에서도 동작합니다. | P1 |
| **J-4** | **에셋 버전 이력과 생성 계보를 보여줍니다.** 버전마다 어떤 프롬프트와 파라미터, 어떤 후처리를 거쳐 나왔는지(B-6)가 붙어 있고, 과거 버전으로 되돌릴 수 있습니다. | P1 |
| **J-5** | 공유 링크에 OG 메타태그와 썸네일을 붙여 메신저·SNS 미리보기가 나오게 하고, iframe 임베드 코드를 제공합니다. | P2 |
| **J-6** | 갤러리 검색과 태그, 좋아요를 제공합니다. | P2 |

**J-3이 이 절의 핵심입니다.** WMT 스키마(6.2절)가 담은 이벤트·오디오 바인딩을 Unity 임포터만이 아니라 **웹 뷰어도 소비합니다.** 같은 계약을 읽는 두 번째 구현체가 생기면서 스키마가 특정 구현에 묶이지 않았다는 사실이 증명되고, 공유받은 사람은 Unity 없이도 "소리 나는 에셋"을 경험합니다. 뷰어는 에디터 번들을 그대로 열지 않고 뷰어 전용의 가벼운 번들로 분리합니다 — 첫 화면이 에디터 코드 전체를 내려받게 하지 않습니다.

**공개에는 책임이 따릅니다.** 공개 전환 시 생성물의 이용 조건을 표시하고(7.2절), 신고 접수 경로와 운영자 비공개 처리 수단을 둡니다. 능동적 모더레이션은 하지 않으며 신고 대응만 합니다.

### K. 협업 — lock 기반

[[ROADMAP]]에 보존했던 설계 중 1단계(권한 기반 배타 편집)를 v2 범위로 승격합니다. **왜 CRDT가 아니라 lock인지의 근거는 로드맵 1.2절에 그대로 있으며, 공간 영역 예약(2단계)과 동시편집(3단계)은 여전히 범위 밖입니다.**

| ID | 요구사항 | 우선 |
| --- | --- | :---: |
| **K-1** | **프로젝트에 다른 사용자를 초대합니다.** 역할은 편집자와 열람자 둘이면 충분합니다. | P2 |
| **K-2** | **프레즌스를 표시합니다.** 지금 이 프로젝트를 누가 열고 있는지, 누가 어느 노드를 잠갔는지가 화면에 보입니다. | P2 |
| **K-3** | **노드 단위 lock을 제공합니다.** 노드를 편집하려면 lock을 얻어야 하고, 다른 사람이 잡은 노드는 읽기 전용으로 표시됩니다. lock은 TTL 리스이며 하트비트가 끊기면 자동 해제됩니다 — 브라우저를 닫고 떠난 사람이 노드를 영원히 잠그지 못하게 합니다. | P2 |
| **K-4** | **커맨드 브로드캐스트로 씬을 동기화합니다.** lock 보유자가 실행한 커맨드가 STOMP로 같은 세션의 다른 참여자에게 전파되어 각자의 씬에 재생됩니다. 전파되는 것은 씬 전체가 아니라 커맨드이며, 이것이 1단계 커맨드 스택 설계를 재사용하는 지점입니다. | P2 |
| **K-5** | lock 요청과 이양을 제공합니다. 잠긴 노드에 편집을 시도하면 소유자에게 요청이 가고, 소유자는 넘겨줄 수 있습니다. | P2 |

**K-4가 커맨드 스택 설계의 세 번째 소비자입니다.** 첫째가 undo/redo, 둘째가 F절 조수, 셋째가 협업 전파입니다. 커맨드가 직렬화 가능하고 결정적으로 재생되면 협업의 배관은 STOMP 전송뿐이며, 이 조건은 1단계에서 커맨드를 설계할 때부터 요구사항입니다 — **협업을 나중에 얹는 것이 아니라, 커맨드의 직렬화 가능성을 처음부터 요구하는 방식으로 비용을 앞당겨 지불합니다.**

전송 계층은 WebSocket과 STOMP로 충분합니다. lock 방식은 초당 수백 건의 메시지가 오가지 않고 락의 획득·해제와 커맨드 전파 정도만 흐르기 때문이며, `3DCommunity`의 STOMP 경험을 그대로 재사용합니다.

### L. VLM 검수자 — 검수자 역할

[[ROADMAP]]에 보류로 남겼던 네 번째 AI 역할을 v2 범위로 승격합니다. 생성기·후처리기·조수에 검수자가 더해져 **생성 → 정리 → 다듬기 → 평가**의 네 역할이 완성됩니다.

## 6. 데이터 설계

### 6.1 glTF가 담을 수 없는 것

**glTF에는 오디오도 애니메이션 이벤트도 담을 수 없습니다. 따라서 `extras`에 커스텀 스키마를 두는 것이 유일한 현실적 경로입니다.**

확인한 내용은 이렇습니다. Khronos가 비준한 확장 가운데 오디오를 다루는 것이 없습니다. `KHR_audio_emitter`는 디렉터리 자체가 존재하지 않고, `KHR_audio_graph`는 아직 제안 단계에 머물러 있습니다. `MSFT_audio_emitter`가 있기는 하나 벤더 확장이고 Babylon만 지원하기 때문에 three.js를 쓰는 이 프로젝트에서는 선택지가 되지 못합니다.

애니메이션 쪽은 조금 더 따져볼 여지가 있었습니다. glTF의 기본 애니메이션 채널은 위치와 회전, 스케일, 모프 가중치의 네 가지뿐이지만, **`KHR_animation_pointer`가 비준 확장으로 존재해 JSON 포인터로 머티리얼이나 카메라 같은 임의 속성까지 애니메이션할 수 있습니다.** 그럼에도 결론은 달라지지 않습니다. 이 확장이 넓히는 것은 **무엇을 움직일 수 있는가**이지 **특정 시점에 이름 붙은 사건을 남기는 수단**이 아니며, 이벤트라는 개념은 여전히 명세 어디에도 없습니다.

이 외에도 glTF가 담지 못하는 것들이 있습니다. IK와 본 컨스트레인트, 머티리얼 노드 그래프, 물리와 콜라이더, 스테이트 머신과 블렌드 트리, 커스텀 셰이더가 여기에 해당합니다. 스키닝은 정점 하나가 최대 네 개의 본에만 영향을 받으며 세트를 추가하면 넘길 수 있고, 모프 타깃은 런타임에서 상위 여덟 개까지만 반영됩니다. 이런 제약들은 설계 단계에서 미리 전제해야 나중에 되돌아가는 일이 줄어듭니다.

### 6.2 `extras` 스키마 설계

**애니메이션에는 이벤트를, 씬 루트에는 오디오 클립 목록을 각각 `extras`에 담고, 이벤트가 클립을 이름으로 참조하는 구조로 설계합니다.**

이렇게 나눈 이유는 하나의 효과음을 여러 애니메이션에서 재사용할 수 있어야 하기 때문입니다. 클립 실체를 이벤트마다 중복해 넣는 대신 한곳에 모아두고 참조만 하도록 하면, 같은 타격음을 여러 모션에서 공유할 수 있고 파일 크기도 불필요하게 늘지 않습니다.

**시각은 프레임이 아니라 초로 저장하며, 이것이 유일한 정본입니다.** glTF 애니메이션의 시간축과 Unity의 `AnimationEvent`가 모두 초 단위인데, 그 사이에서 Unity는 임포트할 때 클립을 자체 프레임레이트로 다시 샘플링합니다. 프레임 번호를 정본으로 삼으면 이 재샘플링에서 어긋나므로, 초를 기준으로 두고 프레임은 화면 표시를 위한 참고값으로만 함께 담습니다.

> **필드 이름과 타입, 필수 여부, 검증 단언은 [[WMT_SCHEMA|WMT 스키마 v1]]에 있습니다.** 익스포터와 Unity 임포터, 그리고 **v2에서 더해진 공유 뷰어(J-3)**가 공유하는 계약이므로 그 문서를 정본으로 삼으며, 여기에 옮겨 적지 않습니다.

설계할 때 지킨 원칙은 네 가지입니다.

첫째, 모든 항목을 `wmt`라는 이름의 네임스페이스 안에 감쌉니다. `extras`는 누구나 자유롭게 쓸 수 있는 자리이므로 다른 도구가 넣은 값과 충돌하지 않게 하기 위해서입니다.

둘째, 스키마에 버전을 함께 담습니다. 나중에 구조를 바꾸더라도 임포터가 버전을 보고 분기할 수 있어야 이미 내보낸 파일이 무용해지지 않습니다.

셋째, **이 스키마를 읽지 못하는 뷰어에서도 모델은 정상적으로 표시되어야 합니다.** `extras`는 명세상 무시해도 무방한 자리이므로, 소리가 나지 않을 뿐 모델이 깨지는 일은 없습니다. 표준을 벗어나면서도 호환성을 잃지 않는 지점이 여기입니다.

넷째, 생성 출처를 함께 남깁니다. 어떤 프롬프트로 만든 소리인지 기록해두면 나중에 같은 결과를 다시 얻거나 조금 바꿔 다시 만들 수 있습니다.

### 6.3 Unity 임포터가 하는 일

**임포터는 glTF가 표현하지 못한 부분을 Unity의 기존 기능으로 복원하는 역할을 합니다.**

glTFast나 UnityGLTF가 모델을 먼저 가져오면, 뒤이어 후처리 스크립트가 `extras`의 `wmt` 영역을 읽습니다. 먼저 오디오 클립 목록을 훑어 각 파일을 Unity의 `AudioClip` 에셋으로 임포트합니다. 그다음 애니메이션마다 기록된 이벤트를 Unity의 `AnimationEvent`로 변환해 해당 클립의 지정된 시각에 꽂습니다. 마지막으로 이 이벤트를 받아 소리를 재생하는 리시버 컴포넌트를 프리팹에 붙이면, 애니메이션을 재생하는 것만으로 정해진 프레임에 효과음이 울립니다.

**이 항목의 결과물은 기능 자체보다 설명 가능성에 있습니다.** 표준에 해당 기능이 없다는 사실을 확인하고, 그 위에서 직접 스키마를 설계한 뒤, 엔진 쪽 임포터까지 붙여 끝을 맺은 과정이 2절의 두 번째 평가 기준과 정확히 맞물립니다.

### 6.4 서버 데이터 모델

사용자와 프로젝트, 에셋 버전, 생성 잡, 크레딧 원장, 공유 링크의 테이블 설계는 **[[ARCHITECTURE]] 4절이 정본입니다.** 이 문서에는 요구사항과의 대응만 남깁니다 — I절은 `users`·`credit_ledger`, J절은 `assets`·`asset_versions`·`share_links`, H-8은 `scene_revisions`, B-4·H-3은 `generation_jobs`에 대응합니다.

## 7. 범위 밖

아래 항목들은 v2에서도 제외합니다. 검토를 마친 설계는 폐기하지 않고 [[ROADMAP]]에 근거와 함께 남겨두었습니다. **v1에서 범위 밖이던 협업 1단계와 VLM 검수자는 v2 범위로 승격되어 이 표에서 빠졌습니다.**

| 항목 | 제외한 이유 |
| --- | --- |
| **협업 2·3단계** — 공간 영역 예약, 동시편집 | lock 기반 1단계(K절)로 협업의 골격은 증명됩니다. 공간 예약은 선행 사례가 없어 자작 리스크가 크고, 동시편집은 3D 위상 변경에서 병합 의미가 정의되지 않습니다. |

### 7.1 도입 금지 — 라이선스 판정

**아래 항목들은 라이선스 문제로 도입할 수 없습니다.** 새로운 모델이나 데이터셋을 검토할 때는 코드와 가중치의 라이선스를 각각 따로 확인해야 합니다. 코드가 MIT여도 가중치가 비상업 조건인 사례가 흔하기 때문입니다.

| 대상 | 사유 |
| --- | --- |
| **Hunyuan3D 2.x 전 계열** | 라이선스 원문의 Territory 정의가 **대한민국을 명시적으로 제외**하고 있습니다. 상업적 이용 여부와 무관하며, fal.ai 같은 호스팅 서비스를 경유하면 지역 제한을 우회할 수 있다는 근거도 확인되지 않았습니다. |

| MoMask / MDM 등 모션 생성 오픈소스 | 코드는 MIT이지만 SMPL과 AMASS, HumanML3D **데이터셋의 학술 목적 제한이 전이**됩니다. |

| Mixamo | 공개 API가 존재한다는 근거가 없고, **모션 파일을 재배포하는 것은 약관 위반입니다.** 이 프로젝트는 저장소를 공개하므로 파일을 번들해 올리는 순간 재배포에 해당합니다. 따라서 런타임 연동과 정적 번들 **모두 제외**합니다. |

라이선스를 확인해 사용 가능한 것으로 판정한 항목은 다음과 같습니다. TRELLIS와 TripoSR은 MIT이고, InstantMesh는 Apache-2.0입니다. UniRig는 코드와 가중치가 모두 MIT이며, xatlas와 glTF-Transform, meshoptimizer는 MIT, Draco는 Apache-2.0입니다. three.js와 공식 에디터는 MIT, Babylon.js Editor는 Apache-2.0입니다.

### 7.2 생성물의 권리 (미확인 — 공개 전 확정 필수)

공개 갤러리(J-1)는 생성물을 제3자에게 노출하므로 **생성물의 이용 권리를 제공자 약관에서 확인해야 합니다.** Tripo와 ElevenLabs의 유료 생성물에 어떤 권리가 부여되는지, 그 권리를 사용자에게 어떤 문구로 전달할지는 **아직 원문을 확인하지 않았습니다.** 갤러리 공개 기능을 켜기 전(마일스톤 M9)에 확인하고 이 절을 채웁니다. 확인 전까지 갤러리에는 임시 문구("생성물의 이용 조건은 각 제공자 약관을 따릅니다")를 둡니다.

## 8. 기술 스택

```
클라이언트     React 19 + TypeScript + Vite
              @react-three/fiber + drei(기즈모) + leva(인스펙터)
              three.js WebGPURenderer — WebGL2 자동 폴백
              Zustand — 씬 그래프 / 커맨드 스택
              Web Audio API
              에디터 번들과 뷰어 번들 분리 (J-3)

공유 모듈      shared/postprocess/ — 런타임 중립
              glTF-Transform + meshoptimizer + Draco + xatlas
              브라우저는 웹워커에서, 서버는 Node 자식 프로세스에서 실행

서버          Spring Boot — 인증(OAuth) / 크레딧 / 외부 API 중계
              작업 큐 / 정본 저장 / STOMP 진행률·협업 중계
              후처리 폴백은 공유 모듈을 Node 자식 프로세스로 실행
              PostgreSQL + S3 호환 오브젝트 스토리지

외부 API      Tripo — 메시 / 텍스처 / 오토리깅 / 모션 리타깃
              fal.ai TRELLIS — 메시 대체 경로
              ElevenLabs Sound Effects — 효과음
              Claude — 자연어 조수 · VLM 검수, tool calling
```

**이 구성을 고른 가장 큰 이유는 기존 자산을 그대로 쓸 수 있다는 점입니다.** `C:/dep/3DCommunity`에서 React와 three.js, Spring Boot의 STOMP, JWT 인증 조합을 이미 다뤄봤기 때문에 학습에 들어갈 시간을 줄이고 이 프로젝트 고유의 문제에 집중할 수 있습니다. PostgreSQL 역시 같은 프로젝트에서 운용한 경험이 있습니다.

두 번째 이유는 1.2절에서 언급한 코드 공유입니다. 후처리 도구 세 가지가 전부 JavaScript와 WebAssembly로 제공되므로, 서버 폴백은 브라우저와 같은 모듈을 그대로 실행합니다. 다만 **이 이점의 크기를 부풀리지 않습니다.** 서버가 실행하는 후처리는 C-2의 UV 언랩 하나뿐이고 그 엔드포인트는 100줄 안팎입니다. Spring Boot는 이 모듈을 **Node 자식 프로세스로 호출하며**, 코드 공유를 위해 서버 런타임을 통째로 바꾸지 않습니다.

서버를 Node로 통일하는 안은 검토 끝에 접었고 경위는 [[DECISIONS]] D-9에 있습니다. Babylon.js Editor는 v5가 Electron 기반 데스크톱 애플리케이션이어서 재사용할 자산이 없어 접었습니다.

### 8.1 저장소 구조

**단일 저장소로 갑니다.** 기능별로 원격 저장소를 나누면 `shared/postprocess/`가 갈라져 코드 공유라는 이점이 사라지고, 생성부터 Unity까지 관통하는 데모 레일을 한 명령으로 돌릴 수 없게 됩니다.

```
web-multiAI-tool/
  client/          React + R3F 에디터 + 공개 화면(갤러리·뷰어)
  server/          Spring Boot
  shared/
    postprocess/   런타임 중립 — 브라우저와 Node 양쪽에서 무수정 실행
    types/         작업 상태 DTO, 단가표, WMT 스키마 타입
  unity/           C# 임포터
  fixtures/demo/   데모 레일 픽스처
  docs/
```

나중에 떼어낼 후보는 `unity/` 하나뿐입니다. UPM이 git 저장소의 하위 폴더를 직접 설치할 수 있으므로 지금 나눌 필요는 없습니다.

### 8.2 되돌릴 수 있게 두는 제약

서버 런타임 결정을 나중에 뒤집더라도 비용이 크지 않도록 아래를 지킵니다.

**`shared/postprocess/`를 런타임 중립으로 유지합니다.** `node:*`도 `window`나 DOM도 import하지 않으며, 입력은 `ArrayBuffer`와 옵션, 출력은 `ArrayBuffer`와 리포트입니다. 그러면 같은 모듈이 웹워커에서도, Node 서버에서도, Spring이 띄운 자식 프로세스에서도 무수정으로 돕니다.

**서버를 쓰기 전에 HTTP 계약을 먼저 확정합니다.** 클라이언트는 프레임워크가 아니라 계약에 대고 코딩합니다. 계약은 [[ARCHITECTURE]] 5절입니다.

**클라이언트의 서버 호출은 한 파일만 거칩니다.** 컴포넌트에 `fetch`를 흩뿌리지 않습니다.

**작업의 영속 정체성은 제공자가 준 작업 ID입니다.** 진실의 원천은 외부 API이고 우리 레코드는 포인터이므로, 서버를 다시 써도 진행 중인 작업이 살아남습니다.

**서버는 씬을 해석하지 않습니다.** 씬 리비전은 불투명한 블롭이고 서버가 아는 것은 버전 번호와 소유권뿐입니다. v2에서 서버가 정본 저장을 맡게 되었지만(H-8) 이 원칙은 유지됩니다 — 도메인을 모르는 서버는 교체가 쉽습니다.

### 8.3 차용 — three.js 공식 에디터

**A절의 기본기 항목들은 직접 설계하지 않고 three.js 공식 에디터의 Command 패턴을 차용합니다.**

undo와 redo, 씬 직렬화, 다중 선택, 카메라 조작은 화면에 드러나지 않으면서 개발 기간을 크게 소모하는 영역입니다. 공식 에디터가 MIT 라이선스라 가져다 쓰는 데 법적 문제가 없고, 이미 검증된 구조이므로 설계에 시간을 들이지 않아도 됩니다.

v2에서 차용에 요구사항이 하나 더해집니다. **커맨드는 처음부터 직렬화 가능해야 합니다.** undo/redo(A-5)와 조수(F-3), 협업 전파(K-4)가 모두 같은 커맨드 객체를 소비하므로, 커맨드가 JSON으로 오가고 결정적으로 재생되는 성질이 1단계 설계 시점의 완료 조건에 들어갑니다.

| **서비스 범위 확장이 코어 데모를 지연시킵니다.** v2의 가장 새로운 위험입니다. | 우선순위 구조가 방어선입니다 — P0(데모 A)를 먼저 끝내고 P1(서비스)로 갑니다. 서버 스키마에 `user_id` 자리만 파두는 것 외에, 서비스 기능이 P0 단계의 완료 조건에 끼어들지 않습니다. |
| 범위가 예산을 넘어섭니다. | P0만으로 데모 A가, P0+P1으로 데모 B가 성립하도록 구성했습니다. P2는 잘라내도 두 데모가 무너지지 않습니다. |

## 11. 완료 조건

**완료 조건은 두 겹입니다.**

**코어 완료 — 데모 A.** 1.4절의 대표 데모를 한 번의 세션 안에서, 브라우저만으로, 캐릭터 생성부터 Unity 재생까지 끊김 없이 시연할 수 있어야 합니다. P0 항목 전부가 동작해야 합니다.

**서비스 완료 — 데모 B.** 1.5절의 장면 — 낯선 사용자가 공개 URL로 접속해 갤러리를 보고, 가입하고, 무료 크레딧으로 에셋을 만들어 공유 링크를 발행하고, 다른 기기에서 그 링크가 소리와 함께 재생되는 것 — 을 실제 배포 환경에서 시연할 수 있어야 합니다. P1 항목 전부가 동작해야 합니다.

여기에 부가 조건이 따라붙습니다. 각 기술 선택의 근거를 문서로 제시할 수 있어야 하며(평가 기준 2), 구현하지 않은 설계 — 공간 예약과 동시편집, 결제 — 가 근거와 함께 [[ROADMAP]]에 남아 있어야 합니다. 7.2절의 생성물 권리 확인이 갤러리 공개 전에 끝나 있어야 합니다.
