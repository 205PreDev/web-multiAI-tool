# 의사결정 기록

무엇을 만드는지는 [[REQUIREMENTS]]에 있습니다. **이 문서는 무엇을 고르지 않았고 왜인지를 남깁니다.**

검토를 마치고 접은 대안은 그 자체가 자산입니다. 채택한 것만 적어두면 나중에 같은 논의가 반복되고, 왜 그렇게 했느냐는 물음에 답할 수 없습니다.

각 항목은 **결정 / 배경 / 접은 대안 / 파급**으로 씁니다. 뒤집힌 결정은 지우지 않고 뒤집힌 사실을 함께 남깁니다.

## D-1. 목표를 포트폴리오와 기술 증명으로 잡는다

**2026-08-04**

상용 서비스 출시도, 본인 실사용도 목표가 아닙니다.

이 결정이 뒤따르는 판단의 절반을 정합니다. 시장 규모와 경쟁사 요금제, 지불 의사를 조사할 필요가 없어지고, **같은 일을 하는 경쟁 서비스가 이미 있다는 사실이 치명적이지 않게 됩니다.** 상용이라면 기획을 접을 근거지만 여기서는 아닙니다. 대신 평가 기준이 완성도와 설명 가능성 둘로 좁혀집니다.

**접은 대안** — 상용을 전제로 한 기획. 그 경우 3D 생성 시장의 경쟁 밀도상 차별점을 만들기 어렵고, API 원가 구조상 단가도 맞추기 어렵습니다.

**파급** — 이 문서가 존재하는 이유이기도 합니다. 설명 가능성이 평가 기준이므로 판단의 근거를 남기는 것 자체가 산출물입니다.

## D-2. 경쟁축을 3D 생성 서비스로 잡는다

**2026-08-04**

초기 구상은 "웹에서 도는 3D 에디터"였습니다. 그 축을 멀티모달 AI로 옮기면 경쟁 상대와 웹인 이유가 함께 바뀝니다.

| | 초기 구상 | 확정 |
| --- | --- | --- |
| 정체성 | 웹 3D 에디터 | AI 네이티브 3D 에셋 제작 도구 |
| 직접 경쟁 | Blender, Maya, Spline | Meshy, Tripo, Rodin |
| 웹인 이유 | 설치·라이선스 비용 회피 | 무거운 추론이 서버에 있으므로 클라이언트는 얇아도 됨 |
| 차별점 | 협업 기능 | 생성 이후를 책임짐 |

**가장 중요한 변화는 "웹이어야 하는 이유"입니다.** "설치비가 아까워서"는 "Blender는 무료다"로 반박당하는 약한 논거였습니다. 멀티모달을 축으로 두면 구조적 논거가 됩니다 — 추론은 어차피 서버에서 돌고 클라이언트는 뷰어와 에디터면 충분하므로, 오히려 데스크톱 앱이 부자연스러운 구조입니다.

**접은 대안** — Blender·Maya와 겨루는 축. 기능 수로는 이길 수 없습니다. Meshy·Tripo와 겨루면 **생성 이후**라는 빈 자리가 드러나고, 그 자리가 D-4의 후처리기 역할로 이어집니다.

## D-3. AI에 세 역할을 맡긴다

**2026-08-04**

생성기와 후처리기, 조수 셋을 함께 채택했습니다.

**세 개를 함께 고른 것이 핵심입니다.** 생성만으로는 Meshy·Tripo와 같은 물건이 됩니다. 후처리가 붙어야 게임에 실제로 쓸 수 있는 에셋이 되고, 조수가 붙어야 3D 조작이라는 진짜 장벽이 내려갑니다. 세 역할이 **생성 → 정리 → 다듬기**라는 하나의 흐름을 이룹니다. 기능 셋을 나열한 것이 아니라 파이프라인 하나를 고른 것입니다.

**접은 대안** — 검수자. VLM이 렌더 뷰를 보고 문제점을 지적하는 역할입니다. **배제가 아니라 보류**이며 근거와 방법론은 [[ROADMAP]]에 남겼습니다. GPTeval3D의 pairwise 비교 방법론이 확인됐고 구현 난이도도 낮지만, 핵심 세 역할을 제대로 마무리하는 쪽이 우선입니다.

## D-4. 후처리 순서를 정리 → UV → 리깅 → LOD로 고정한다

**2026-08-04**

AI가 생성한 메시는 토폴로지가 정돈되어 있지 않은 경우가 많고, **이 상태로 리깅에 들어가면 리깅 품질까지 함께 무너집니다.**

**접은 대안** — 생성 직후 곧바로 리깅. 외부 API가 알아서 처리해줄 것이라는 기대였는데, 리깅 품질이 입력 토폴로지에 종속된다는 점이 확인되어 접었습니다.

**파급** — 이 순서가 이 프로젝트의 핵심 설계 판단인데 검증 수단이 없다는 지적을 받아, **한 번 측정해 표로 남기기로 했습니다**(REQUIREMENTS 4절 C). 정리와 UV를 거친 리깅과 곧바로 한 리깅을 비교합니다. 결과가 예상과 다르면 순서 고정 자체를 재검토합니다. 결론을 근거보다 오래 살려두지 않습니다.

## D-5. 자동 리깅을 외부 API로 처리한다

**2026-08-04**

자체 GPU에 오픈소스 모델을 호스팅하지 않고 Tripo API를 씁니다.

UniRig는 코드와 가중치가 모두 MIT라 라이선스 장벽이 없지만 CUDA 8GB VRAM을 상시 요구합니다. 1인 개발에서 GPU 인스턴스 비용과 콜드스타트는 감당하기 어렵습니다.

**Tripo 오토리깅이 건당 $0.25이며 2026-08-08에 공식 가격표와 대조해 확인했습니다.** 이 단가가 결정 전체를 지탱합니다.

**접은 대안** — UniRig 자체 호스팅. 되살릴 조건은 [[ROADMAP]]에 있습니다.

## D-6. 협업을 1차 범위에서 제외한다

**2026-08-04**

멀티모달을 증명하는 것은 협업이 아니라 **메시와 애니메이션, 오디오가 하나의 타임라인에서 묶여 단일 산출물로 나오는 장면**입니다. 협업은 그 논거와 직접 연결되지 않습니다.

부수적으로 협업 데모는 혼자 시연하기 어렵고, 공간 영역 예약은 전문 3D 에디터 영역에 선행 사례가 없어 설계와 검증을 전부 자작해야 합니다.

**설계는 폐기하지 않고 [[ROADMAP]]에 보존했습니다.** lock 우선 판단과 그 근거는 검증까지 끝난 상태입니다. 게임업계가 병합 불가능한 바이너리 에셋에 exclusive checkout을 쓴다는 점, 3D에서는 **위상 변경**이 동시에 일어나면 CRDT 병합 결과의 의미가 정의되지 않는다는 점이 그것입니다. **구현하지 않아도 설명 가능한 설계는 포트폴리오 자산입니다.**

**접은 대안** — Yjs 같은 CRDT를 붙이는 것. 근거 없이 붙이는 것보다 왜 lock인지를 도메인 특성으로 설명할 수 있는 쪽이 기술 증명으로 낫습니다.

## D-7. glTF `extras`에 자체 스키마를 둔다

**2026-08-04 / 2026-08-08 보강**

**표준에 방법이 없음을 확인한 뒤 내린 결정입니다.** Khronos 비준 확장에 오디오가 없고, `KHR_audio_emitter`는 디렉터리 자체가 없으며, `KHR_audio_graph`는 제안 단계입니다. `MSFT_audio_emitter`는 벤더 확장이고 Babylon만 지원해 three.js에서는 선택지가 아닙니다.

**접은 대안** — 표준 확장을 기다리거나 벤더 확장에 기대는 것. 둘 다 데모를 성립시키지 못합니다.

**2026-08-08 정정** — "애니메이션 채널은 위치·회전·스케일·가중치뿐"이라고 적었던 근거가 틀렸습니다. `KHR_animation_pointer`가 비준 확장으로 존재해 JSON 포인터로 임의 속성까지 애니메이션할 수 있습니다. **결론은 유지됩니다** — 이 확장이 넓히는 것은 무엇을 움직이는가이지 특정 시점에 이름 붙은 사건을 남기는 수단이 아닙니다. 다만 근거 문장이 틀렸다는 사실을 남깁니다.

계약은 [[WMT_SCHEMA]]가 정본입니다. 익스포터와 Unity 임포터가 다른 언어로 만들어지는 두 구현체라 계약이 없으면 각자 다르게 해석합니다.

## D-8. 이벤트 시각을 프레임이 아니라 초로 저장한다

**2026-08-08**

편집기는 사용자에게 프레임을 보여주지만 저장되는 정본은 초입니다.

**Unity는 임포트할 때 클립을 자체 프레임레이트로 다시 샘플링합니다.** 프레임 번호를 정본으로 삼으면 이 재샘플링에서 어긋납니다. glTF 애니메이션의 시간축과 Unity의 `AnimationEvent`가 모두 초 단위이므로, 초를 기준으로 두면 재샘플링과 무관하게 값이 보존됩니다.

**접은 대안** — 프레임 번호를 정본으로 두고 fps를 함께 저장하는 방식. 편집기 안에서는 자연스럽지만 엔진 경계를 넘지 못합니다.

## D-9. 서버를 Spring Boot로 유지한다

**2026-08-08 — 검토 끝에 뒤집혔다가 원복된 결정**

후처리 폴백은 `shared/postprocess/`를 **Node 자식 프로세스로 실행**합니다.

검토 과정에서 한 번 뒤집혔습니다. "브라우저와 서버가 같은 코드를 공유한다"를 웹과 three.js 선택의 근거로 두 번 내세우면서 정작 JS를 돌릴 런타임이 스택에 없다는 지적이 있었고, Node 단일화 권고가 나왔습니다. **그 권고는 다시 철회됐습니다.** 이유가 셋입니다.

1. **선택지가 잘못 만들어졌습니다.** Node를 별도 HTTP 서비스 형태로만 검토하고 자식 프로세스 형태를 빠뜨렸습니다. 후자면 같은 모듈을 그대로 돌리면서 두 번째 서비스도 배포도 인증 경계도 생기지 않습니다. 늘어나는 것은 서버 호스트에 Node가 있어야 한다는 것 하나입니다.
2. **코드 공유의 이점을 과대평가했습니다.** 서버가 실행하는 후처리는 C-2의 UV 언랩 하나뿐이고 엔드포인트는 100줄 안팎입니다. 게다가 "JVM에서 별도 구현하는 비용"이라는 비교항 자체가 없습니다 — xatlas는 C++이라 아무도 Java로 재구현하지 않습니다.
3. **판단 기준을 잘못 적용했습니다.** "1인이 다뤄야 할 기술 영역 수"를 기준으로 삼으면서 런타임 개수를 셌는데, **익숙하지 않은 것의 개수**를 셌어야 했습니다. Node 단일화는 서버측 Node 관용구라는 새 영역을 추가합니다.

**접은 대안** — Node 단일화, Node 사이드카, 폴백 포기. 되살릴 조건은 REQUIREMENTS 8.2절에 있습니다.

**파급** — 결정을 서두르는 것보다 **`shared/postprocess/`를 런타임 중립으로 유지하는 제약**이 우선입니다. `node:*`도 DOM도 import하지 않고 입출력을 `ArrayBuffer`로 두면 어느 런타임에서도 무수정으로 돌아, 이 결정을 되돌리는 비용이 거의 0이 됩니다.

## D-10. 저장소를 나누지 않는다

**2026-08-09**

기능별로 원격 저장소를 나누는 방안을 검토했다가 접었습니다.

`shared/postprocess/`가 갈라지면 코드 공유라는 이점이 사라지고, 생성부터 Unity까지 관통하는 데모 레일을 한 명령으로 돌릴 수 없게 됩니다. 저장소 분리는 사람이 여럿이고 릴리스 주기가 다를 때 값을 하는데, 1인 개발에서는 하나의 논리적 변경이 PR 여러 개로 쪼개지는 비용만 생깁니다.

**떼어낼 후보는 `unity/` 하나뿐입니다.** 소비자와 툴체인이 다르지만, UPM이 git 저장소의 하위 폴더를 직접 설치할 수 있으므로 지금 나눌 이유가 없습니다.

## D-11. 문서를 저장소 안 마크다운으로 관리한다

**2026-08-09**

노션으로 옮기는 방안을 검토했다가 접었습니다.

작업 문서는 매 세션 읽히고, 미지 에이전트 검증이 직접 읽어야 하며, 라이선스 CI의 검사 대상이기도 합니다. 저장소 밖으로 나가면 이 셋이 전부 막힙니다. **문서 변경이 코드 변경과 같은 diff에 남는 것**도 설명 가능성에 직결됩니다.

**접은 대안** — 노션으로 이전. 발표용 페이지는 성격이 다른 별도 산출물이므로 데모가 나온 뒤에 따로 만듭니다.

## D-12. 검증을 네 층으로 나눈다

**2026-08-08**

0차 데모 레일, 1차 도구 검증, 2차 미지 에이전트 검증, 3차 사용자 검증입니다.

**0차가 이 설계의 핵심입니다.** 완료 조건이 대표 데모 하나뿐인데 그 하나를 마지막 단계에서만 확인하는 구조였습니다. 각 단계 산출물을 픽스처로 커밋하고 외부 API 없이 하류만 재검사하면 비용 0으로 매 PR에서 돕니다.

**2차의 조건은 판단 근거를 주지 않는 것입니다.** 왜 그렇게 했는지를 알면 냉정한 검토가 되지 않습니다. **이 문서도 2차 에이전트에게 넘기지 않습니다** — 공개 문서인 것과 검토자에게 주는 것은 별개입니다.

**접은 대안** — 사람 체크리스트. 잊힙니다. 그리고 검증 층을 더 쌓는 것 — 1인 개발에서 감당할 수 없는 절차는 실행되지 않고 규칙만 죽습니다.

## D-13. 목표를 공개 서비스급으로 확장한다

**2026-08-10 — D-1의 부분 개정**

포트폴리오와 기술 증명이라는 v1 목표는 유지하되, **낯선 사용자가 URL로 접속해 쓸 수 있는 공개 웹 서비스로 완성하는 것**이 더해졌습니다. 사용자의 명시적 방향 전환입니다 — "단순히 포트폴리오 목적이 아니라 하나의 완성도 높은 잘 만든 웹 프로젝트".

평가 기준이 둘에서 셋(완성도 / 설명 가능성 / 서비스 품질)이 되고, 우선순위의 의미가 재정의됐습니다 — P0는 데모 A(파이프라인), P1은 데모 B(공개 서비스), P2는 확장. 완료 조건도 두 겹이 됐습니다.

**수익화는 여전히 비목표입니다.** 결제·구독은 범위 밖으로 남습니다. "서비스급"의 의미는 돈을 받는 것이 아니라 낯선 사용자에게 내놓아도 성립하는 품질 — 인증, 쿼터, 남용 방어, 공유, 이해 가능한 실패 — 입니다.

**접은 대안** — ① 배포 없이 품질 기준만 제품 수준으로 올리는 것: 인증·쿼터·남용 방어가 설계에서 빠져 "서비스급"이 검증 불가능한 주장으로 남습니다. ② 지인 공개 수준: 온보딩과 갤러리가 빠져 데모 B가 성립하지 않습니다.

**파급** — H-6·H-7이 신설 I절로 이관 승격, J절(허브·공유)·K절(협업)·L절(검수자) 신설, [[ARCHITECTURE]]와 [[UX]] 문서 신설. v1의 "서버를 공개 URL에 노출하지 않는다"(H-6 각주)는 폐기됐습니다.

## D-14. 씬 저장을 로컬 우선 + 서버 리비전 동기화로 확장한다

**2026-08-10 — H-1의 확장, "서버는 도메인을 모른다" 원칙은 유지**

v1은 IndexedDB가 유일한 정본이었고 서버는 씬을 아예 갖지 않았습니다. 공유 링크와 협업, 다중 기기가 전부 서버 쪽 기준본을 요구하므로 **서버에 불변 리비전(append-only)을 쌓는 동기화가 더해졌습니다(H-8).**

지킨 것 — **로컬 우선.** 편집은 서버 없이 계속되고 데모 A는 여전히 로컬만으로 성립합니다. **서버는 리비전을 해석하지 않습니다** — 블롭과 seq, 소유권만 압니다.

**충돌은 병합하지 않습니다.** 같은 계정의 두 기기 동시 편집이라는 드문 경우를 위해 3-way 병합을 만드는 것은 비례하지 않으므로, "서버 것 받기 / 내 것으로 저장(과거는 이력에 보존)" 두 선택지로 끝냅니다. 협업 충돌은 lock이 애초에 막습니다.

**접은 대안** — ① 서버 정본 단일화: 오프라인·서버 다운 시 에디터가 죽습니다. v1이 지킨 가치를 버릴 이유가 없습니다. ② CRDT 동기화: 협업을 lock으로 정한 마당에(D-6, D-17) 동기화만 CRDT로 하는 것은 복잡도가 목적을 초과합니다.

## D-15. 인증을 소셜 OAuth로만 둔다

**2026-08-10**

Google·GitHub OAuth만 제공하고 **자체 이메일·비밀번호 가입을 두지 않습니다.**

근거 셋 — 비밀번호 저장·재설정·유출 대응이라는 보안 표면 전체가 사라지고, 가입 봇 억제를 OAuth 제공자의 계정 검증에 떠넘기며, 데모 B 온보딩이 클릭 두 번이 됩니다. 세션은 자체 JWT를 HttpOnly 쿠키로 — `3DCommunity`의 JWT 경험을 재사용하되 localStorage 보관이라는 그 프로젝트의 약점은 반복하지 않습니다.

**접은 대안** — ① 이메일+비밀번호: 위 세 근거의 역방향 비용. ② Supabase Auth 위임: 인증만을 위해 외부 플랫폼 의존을 추가하고, Spring 서버와의 토큰 검증 이원화가 생깁니다. 서버가 이미 있는 구조에서는 얻는 것이 적습니다.

## D-16. 비용을 2중 상한 — 사용자별 크레딧 + 운영자 전역 캡 — 으로 구조화한다

**2026-08-10 — N-6의 재설계**

v1의 월 $40 하드 캡은 개발자 1인의 예산 관리였습니다. 공개 서비스에서는 **누가 얼마나 쓰는가**의 축이 추가되어야 하므로, 사용자별 크레딧 원장(가입 지급 200크레딧, 선차감→실비 정산, 1크레딧=$0.01)과 운영자 전역 캡(개발 기간 $40 유지, 공개 후 환경변수 조정)의 2중 구조로 바꿨습니다.

**전역 캡이 최후의 방어선이라는 v1의 통찰은 그대로입니다** — 모든 사용자별 방어가 뚫려도 월 지출은 상한에서 멈춥니다. 무한대와 상한의 차이가 인증의 유무보다 큽니다.

**결제는 붙이지 않습니다.** 크레딧 충전 경로는 무료 지급과 BYOK(P2)뿐입니다.

**접은 대안** — ① 캡 유지·쿼터 없음: 공개 즉시 남용으로 한 달 예산이 하루에 끝납니다. ② 유료 충전: 수익화는 비목표이고, PG·정산·환불이라는 별개 프로젝트가 열립니다. 로드맵에 여지만 남깁니다.

## D-17. 협업 1단계를 v2 범위로 승격한다

**2026-08-10 — D-6의 부분 뒤집힘**

[[ROADMAP]]에 보존했던 3단계 설계 중 **1단계(권한 기반 배타 편집)만** K절로 승격했습니다. lock이 CRDT보다 낫다는 판정(로드맵 1.2)은 그대로 실행 근거가 됩니다. 공간 영역 예약과 동시편집은 여전히 범위 밖입니다.

승격이 싸진 이유가 있습니다 — **커맨드 스택이 이미 직렬화 가능하도록 설계되기 때문입니다.** undo/redo와 조수(F-3)에 이어 협업 전파(K-4)가 커맨드의 세 번째 소비자가 되면, 협업의 배관은 STOMP 전송뿐입니다. 이 성질을 1단계 커맨드 설계의 완료 조건에 넣는 것으로 비용을 앞당겨 지불했습니다.

**접은 대안** — 협업 전면 승격(공간 예약 포함). 선행 사례 없는 자작 구간을 P2에 넣으면 P2가 P2가 아니게 됩니다.

## D-18. VLM 검수자를 v2 범위로 승격한다

**2026-08-10 — D-3의 보류 해제**

네 번째 AI 역할(검수자)을 L절로 승격했습니다. 생성 → 정리 → 다듬기 → **평가**로 역할 사슬이 닫힙니다.

주장 범위는 로드맵 2.3의 경고를 그대로 계승합니다 — **pairwise 비교까지만.** 절대 점수도 결함 탐지도 주장하지 않습니다. 호출은 사용자 요청 시에만, 크레딧 차감과 함께 — 상시 자동 검수는 비용 구조상(N-6) 넣지 않습니다.

**접은 대안** — 생성 완료마다 자동 검수. 사용자가 요청하지 않은 판정에 크레딧이 나가고, VLM 판정을 파이프라인 게이트로 쓰기에는 신뢰 근거가 부족합니다. 게이트는 C절의 기계 판정만 씁니다.
